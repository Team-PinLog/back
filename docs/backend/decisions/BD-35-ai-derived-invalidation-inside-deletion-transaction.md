# BD-35. AI 파생 데이터 무효화를 삭제 트랜잭션 안에서 백엔드가 직접 쓴다

- **상태**: Accepted
- **날짜**: 2026-07-29
- **관련**: S15P11A705-124, [back#61](https://github.com/Team-PinLog/back/issues/61),
  [BI-21](../implements/BI-21-2026-07-29-ai-derived-invalidation-on-delete.md),
  공용 계약 `Team-PinLog/docs` `static/06_데이터모델_및_무결성.md` §1.3·§6.4~6.9,
  `static/08_API_명세.md` "AI 파생 데이터"

## 맥락

`ai` 스키마의 소유는 AI 파트다(06 §1.3). 그래서 `RecordDeletionService`는 삭제 시 파생 데이터
무효화를 "백엔드의 ai 스키마 연동이 아직 없어서" 빼 놓고 javadoc에 그 사실을 적어 두었다.
그런데 공용 계약은 같은 문서에서 **이 두 컬럼만은 백엔드가 쓴다**고 못 박는다.

| 테이블 | 백엔드 | AI 워커 |
|---|---|---|
| `ai.context_ai_state` | 최초 생성 · `PENDING` · `CANCELLED` · `retry_count` · Finalizer `FAILED` | `PROCESSING` · `COMPLETED` · 작업 중 오류 `FAILED` |
| `ai.context_embedding` | `is_deleted`만 UPDATE | INSERT / UPDATE (`is_deleted` 제외) |

증상은 지금 보이지 않는다. 자연어 검색(`POST /search/records`)이 아직 없기 때문이다. 그런데
검색 제외는 **`context_embedding.is_deleted = false` 필터가 단독으로 담당한다**(MVP는 정확 cosine
검색이라 ANN 인덱스가 없다, 06 §7). 플래그가 꺼진 채 검색이 붙는 순간 삭제한 Context가 결과에
계속 나온다. 자연어 검색이 MVP 시연 범위이므로 이 쓰기가 선행이다.

키워드 쪽은 더 직접적이다. `ai.context_keyword`에는 `is_deleted`에 해당하는 컬럼이 아예 없어,
키워드 조회 제외를 `context_ai_state.keyword_status = 'CANCELLED'`가 **단독으로** 담당한다.

## 선택지

| 안 | 장점 | 단점 |
|---|---|---|
| (a) 삭제 트랜잭션 안에서 백엔드가 직접 UPDATE | core 삭제와 무효화가 원자적. 부분 실패가 없다 | 백엔드가 타 파트 스키마에 쓴다 |
| (b) 커밋 후 이벤트 발행 → AI 워커가 무효화 | 스키마 소유 경계가 코드에서도 깨끗하다 | 커밋과 무효화 사이에 "지웠는데 검색에는 나오는" 창이 열린다. 이벤트 유실 시 영구히 남는다 |
| (c) 별도 트랜잭션(`REQUIRES_NEW`)으로 분리 | 무효화 실패가 삭제를 되돌리지 않는다 | 같은 창이 열린다. 게다가 "삭제는 됐는데 무효화는 실패"가 조용히 남는다 |

## 결정

**(a)** — **제약으로 주어짐**. 06 §6.6이 근거를 명시한다: *"소유는 AI 파트이나 트랜잭션 일관성을
위해 백엔드가 직접 쓴다. 동일 인스턴스이므로 단일 트랜잭션으로 처리된다."* 스키마가 같은
PostgreSQL 인스턴스에 있다는 사실이 (b)·(c)의 유일한 장점(경계의 청결)보다 무겁다 — 이 작업의
목적 자체가 "부분 실패를 남기지 않는 것"이라 분리하면 목적이 깨진다.

제약 안에서 고른 것은 **쓰기 범위를 코드로 좁히는 방법**이다. `AiDerivedDataRepository` 하나에
두 UPDATE만 담고 다른 컬럼에 닿는 경로를 두지 않았다. 이 클래스의 SQL 두 개가 백엔드가 `ai`에
쓰는 전부이며, 리뷰에서 경계 위반을 한 파일만 보고 확인할 수 있다.

`CANCELLED` 전이에 조건을 걸지 않는 것도 계약이 정한 제약이다. `COMPLETED`를 남기면 임베딩
검색에서는 걸러지지만 키워드 조회에서 삭제·탈퇴한 사용자의 Keyword가 계속 노출된다.

## 결과

- 이 결정으로 감수하는 것:
  - **백엔드가 타 파트 스키마에 쓴다.** 컬럼 추가·상태값 변경 같은 AI 쪽 스키마 변경이 백엔드
    코드를 깨뜨릴 수 있다. `ai` 테이블을 JPA 엔티티로 매핑하지 않고 JDBC SQL로 둔 것이 이 결합의
    표면을 SQL 문자열 두 개로 제한한다.
  - **무효화 실패가 삭제 전체를 롤백한다.** `ai` 스키마 장애가 core 삭제까지 막는다. 트랜잭션
    일관성을 택한 대가이며, 계약이 이 방향을 지시한다.
  - **`ai` 테이블에 FK가 없어** 데이터베이스가 정합성을 대신 지켜 주지 않는다. "빠짐"을 잡는 것은
    적용 지점별 테스트뿐이다.
- 재검토 트리거:
  - 회원 탈퇴처럼 대량 Context를 한 번에 지우는 경로가 붙어 `IN` 목록이 커질 때 —
    배치·이벤트 분리를 다시 검토한다(06 §6.9가 이미 배치 분리를 허용한다).
  - `ai` 스키마가 별도 인스턴스로 분리될 때. "동일 인스턴스"가 이 결정의 전제다.
