# BD-39. Embedding Profile은 `application.yml`의 리터럴로 두고 환경변수는 덮어쓰기로만 받는다

- **상태**: Accepted
- **날짜**: 2026-07-29
- **관련**: S15P11A705-135,
  [BI-25](../implements/BI-25-2026-07-29-personal-search-backend-integration.md),
  공용 계약 `Team-PinLog/docs` `static/05_AI_설계.md` §7.1(2026-07-29 개정)·§9.3,
  `ai` 레포 `docs/spec/model-profile.md` §2·§3.1,
  AI 파트 소유 명세 `docs/ai/spec/ai-integration.md` §2.1

## 맥락

`POST /internal/v1/search` 요청 본문의 `embeddingProfile`은 **필수 필드**다. FastAPI는 이 값을 자기
설정과 대조해 다르면 422로 거절하고 양쪽 값을 함께 돌려준다. 빈 결과를 주지 않는 것이 계약이다 —
빈 결과는 "일치하는 기록이 없음"으로 보여 설정 오류를 숨기기 때문이다(`model-profile.md` §3.1).

**Spring이 이 값을 어디서 얻는지가 정해져 있지 않았다.** 공용 계약 §7.1이 그 결정을 이 티켓 시점으로
명시적으로 유예했다 — *"Spring이 그 값을 어디서 얻는지는 검색 연동 시점에 정합니다
(`S15P11A705-135`). 소비자가 없는 상태에서 정하면 붙일 때 다시 뒤집힙니다."*

같은 §7.1은 **오늘 개정됐고**, 개정 전후로 전제가 뒤집혔다.

| | 개정 전 | 개정 후(현행) |
|---|---|---|
| Profile의 정본 | 배포 환경의 단일 설정 | **FastAPI 설정의 기본값**(코드) |
| 환경변수 주입 | 필수 | 실험·롤백용 **덮어쓰기**, 필수 아님 |
| 두 파트의 불일치를 막는 장치 | 단일 주입 | **런타임 대조**(위 422) |

개정 사유는 "Profile 교체가 git 이력도 리뷰도 남기지 않았다"는 것이다. Profile 변경은 기존 Embedding
전부를 조회 대상에서 빼는 결정인데(§9.3 검색 필터의 `embedding_profile` 일치 조건), 그것이 배포 콘솔
편집 한 번으로 가능했다. 값 자체는 §7.1 표에 공개돼 있어 비밀인 적도 없다.

즉 이 티켓이 정할 것은 **Spring 쪽 취득 경로**이고, 판단 기준은 개정된 §7.1이 세운 두 가지다 —
정본은 코드에 두고, 두 파트의 불일치는 런타임 대조로 막는다.

## 선택지

| 안 | 장점 | 단점 |
|---|---|---|
| (a) `application.yml`에 리터럴 + 환경변수 덮어쓰기 | 정본이 git에 있어 교체가 PR·리뷰·이력을 거친다. 값이 항상 존재하므로 런타임 대조가 성립한다. 개정된 §7.1의 FastAPI 쪽 규칙과 대칭이다 | 저장소에 값 문자열이 박힌다(공개 값이라 손해는 없다) |
| (b) 환경변수 필수(`${...}` 기본값 없음) | 개정 **전** §7.1의 "단일 주입"과 같은 모양 | 오늘 뒤집힌 규칙이다. 주입을 빠뜨리면 **빈 문자열 Profile**이 실려 나가 모든 검색이 422로 죽는데, 그 실패가 배포 시점이 아니라 첫 검색 시점에 나타난다 |
| (c) 기동 시 FastAPI에서 조회 | 값이 언제나 상대와 같다 | **대조 장치가 무의미해진다** — 상대 값을 받아 상대에게 되돌려 주는 것이라 항상 일치한다. 기동 순서 의존이 생기고, 상대가 늦게 뜨면 우리도 못 뜬다 |
| (d) 검색 요청마다 FastAPI에서 조회 | 항상 최신 | (c)의 문제에 더해 사용자 검색 경로에 왕복이 하나 더 붙는다 |
| (e) 자바 상수 | 가장 단순 | `AiProperties` javadoc이 명시적으로 거부한 방식이고, 실험·롤백에 재배포가 필요하다 |

## 결정

**(a).** 성격은 **능동적 선택**이다 — §7.1이 결정을 유예했으므로 제약으로 주어진 것이 아니라, 그
절이 세운 기준을 Spring 쪽에 적용해 고른 것이다.

```yaml
pinlog:
  ai:
    embedding-profile: ${PINLOG_AI_EMBEDDING_PROFILE:openai-text-embedding-3-small-1536-cosine-v1}
```

결정적 이유는 둘이다.

**하나. 런타임 대조는 양쪽이 값을 갖는 상태를 전제한다.** §7.1이 "서로 다른 Profile을 갖는 것은
런타임 대조로 막는다"고 쓴 순간, Spring이 값을 갖지 않는 선택지((c)·(d))는 그 문장과 모순이 된다.
상대에게 받은 값을 상대에게 되돌려 주면 대조는 언제나 통과하고, 대조를 통과시키려고 만든 장치가
아무것도 검증하지 않게 된다.

**둘. 정본을 코드에 두는 이유가 Spring 쪽에도 그대로 적용된다.** §7.1의 개정 사유는 "교체가 리뷰를
거치지 않는다"였다. Spring 설정도 같다 — 환경변수만으로 Profile을 바꿀 수 있으면 그 변경이 어디에도
기록되지 않는다. 리터럴을 파일에 두면 교체가 PR이 된다.

**(b)를 버린 이유는 실패 모드다.** 기본값이 없으면 주입 누락 시 Spring은 빈 문자열을 실어 보내고,
FastAPI는 422로 거절하며, 사용자에게는 검색이 통째로 깨진 것으로 보인다. 그 실패가 배포 시점이
아니라 **첫 검색 시점**에 나타나는 것이 나쁘다. 값이 공개 값인 이상 기본값을 두지 않을 이유가 없다.

## 결과

- 이 결정으로 감수하는 것:
  - **같은 값이 두 레포에 있다.** 정본이 `ai` 레포이고 우리 것이 사본이라는 사실은 문서와
    `AiProperties` javadoc에만 있다. 두 값이 어긋나는 것은 런타임 대조가 잡지만, **잡히는 시점은
    배포가 아니라 첫 검색**이다. 배포 시 스모크로 검색을 한 번 태우지 않으면 그 사이가 비어 있다.
  - **`ai` 레포 쪽 대칭이 아직 없다.** 개정된 §7.1은 정본을 `ai` 레포 `app/core/config.py`의
    기본값이라 하고 근거로 `ai` 레포 `docs/proposals/P45-public-config-in-code.md`를 든다. 확인 시점
    (2026-07-29) `config.py`의 `embedding_profile`에는 기본값이 없고(`Field(alias=...)`만 있다) P45
    파일도 없다 — 계약이 먼저 갔고 구현이 아직 따라오지 않았다. 이 결정은 어느 쪽이 되든 성립하지만
    (Spring은 자기 설정값을 실어 보낼 뿐이다), 그 사실은 PR과 결과 패킷에 남긴다.
  - **Profile 전환 절차가 이 결정 안에 없다.** 전환하려면 두 레포를 각각 배포해야 하고 그 사이 구간은
    검색이 422다. 무중단 전환 방법(양쪽 Profile 동시 허용 등)은 §7.1에도 없고 여기서도 정하지 않는다.
- 재검토 트리거:
  - `ai` 레포가 P45를 실제로 구현할 때 — 기본값의 형태가 확정되면 우리 리터럴과 대조해 맞춘다.
  - Profile을 실제로 교체할 때(모델·차원·거리 기준 변경). 전환 절차가 그때 필요해진다.
  - §7.1이 다시 개정될 때. 이 결정은 개정 후 §7.1의 두 기준 위에 서 있다.
