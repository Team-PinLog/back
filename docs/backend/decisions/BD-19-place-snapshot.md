# BD-19. Place는 공용 스냅샷 — 갱신·자동 병합 금지, 검색은 프론트가 직접

## 맥락

Place는 특정 사용자의 소유가 아니라 **전체 회원이 공유하는 공용 데이터**다. 한 행이 여러 사용자의 Record에 연결된다. 여기서 두 가지를 정해야 했다.

1. 카카오 로컬 API를 **누가** 호출하는가 — 서버인가 프론트인가
2. 저장된 Place 행을 카카오의 최신 정보로 **갱신하는가**

## 선택지

**호출 주체**

| 안 | 장점 | 단점 |
|---|---|---|
| (a) 서버가 카카오를 호출 | 응답을 서버가 검증·정규화할 수 있고 키가 노출되지 않음 | 검색 프록시·캐시·재시도·쿼터 관리를 서버가 떠안는다. 지도 SDK가 이미 프론트에 있어 같은 것을 두 번 부르는 구조가 된다 |
| **(b) 프론트가 직접 호출, 서버는 전달값을 upsert** | 저장이 필요한 순간에만 서버가 관여한다. 검색 트래픽이 서버를 지나지 않는다 | 서버가 전달값을 검증할 수 없다. 클라이언트가 보낸 장소 데이터를 신뢰해야 한다 |

**갱신 여부**

| 안 | 장점 | 단점 |
|---|---|---|
| (c) 재전달 시 기존 행을 최신 값으로 갱신 | 상호 변경·이전이 반영됨 | 한 행이 여러 사용자의 Record에 걸려 있어, 갱신하면 **다른 사용자 기록의 장소 정보까지 바뀐다** |
| **(d) 저장 시점 스냅샷 — 재사용하되 갱신하지 않음** | 남의 기록을 건드리지 않는다. 최신 정보는 `place_url`로 카카오맵에 위임 | 상호 변경·폐업이 반영되지 않는다 |

## 결정

**(b)와 (d)를 채택한다. 능동적 선택.**

- **호출은 프론트가 한다.** 카카오에서 받은 정보를 전부 백엔드에 쌓아두지 않고 **저장이 실제로 일어나는 타이밍에만** 서버로 넘긴다. 조회(모아보기·지도)는 DB 전용이며 카카오를 재호출하지 않는다.
- **식별은 `kakao_place_id`로 한다.** 좌표는 표시·지도용이며 식별키가 아니다. 카카오가 동일 장소의 좌표를 미세 조정하고, 한 좌표에 다수 점포가 있으며, 층·호 정보가 응답에 없어 좌표 기반 매칭은 확률적이다.
- **저장 후 갱신하지 않는다.** 동일 `kakao_place_id` 재전달 시 기존 행을 그대로 재사용한다.
- **자동 병합을 금지한다.** 이름·좌표 근접 기반 동일성 판정은 확률적이라, 잘못 병합하면 **타인의 장소에 내 맥락이 붙는 사고**가 된다. 중복이 실제 문제가 되면 운영자 수동 병합 도구로 대응한다.

동시 요청 대비로 저장은 `INSERT ... ON CONFLICT (kakao_place_id) DO NOTHING` 후 재조회한다.

## 결과

**감수하는 것**

- **서버가 장소 데이터를 검증하지 못한다.** 클라이언트가 보낸 값을 그대로 저장한다. 좌표 범위 `CHECK`가 파싱 오류 정도만 잡아준다([BD-10](BD-10-integrity-in-database.md)).
- **스냅샷이 낡는다.** 상호 변경·이전·폐업이 반영되지 않는다. 최신 정보는 `place_url`을 통해 카카오맵에 위임한다.
- **id가 바뀌면 중복이 생긴다.** 폐업 후 재등록이나 카카오 병합으로 `kakao_place_id`가 바뀌면 동일 실제 장소가 별개 Place로 저장된다. 사용자 관점 영향은 미미하고, 장소로 내 Record를 찾는 조회는 miss 후 신규 저장 경로로 빠지므로 오류가 아니다.
- Place에는 `deleted_at`을 두지 않는다. 공용 데이터이므로 Record 삭제나 회원 탈퇴로 지우지 않는다([BD-08](BD-08-soft-delete-no-restore.md)의 예외).

**재검토 트리거**

- **이 결정은 다시 논의하기로 명시되어 있다.** 카카오 호출 주체를 프론트에 둔 선택은 확정이 아니라 현재 합의이며, 서버 검증이 필요해지는 요구가 나오면 재논의한다.
- 갱신을 도입하게 되면 두 가지가 함께 필요하다 — Record에 저장 시점 장소명 스냅샷 컬럼, 그리고 좌표가 임계값 이상 이동하면 동일 장소가 아닐 수 있으므로 갱신을 보류하는 가드.
