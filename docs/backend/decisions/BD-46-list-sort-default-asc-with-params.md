# BD-46. 목록 기본 정렬을 오래된순으로 하고, 방향은 프론트가 상수 파라미터로 준다

- **상태**: Accepted
- **날짜**: 2026-08-03
- **관련**: Jira 작업 · [docs#42](https://github.com/Team-PinLog/docs/pull/42) · [docs#37](https://github.com/Team-PinLog/docs/pull/37) (계승됨)

## 맥락

docs#37이 "Library 책장 정렬은 `created_at ASC`"를 명문화하려다 두 가지가 드러났다. 구현은 전부 `DESC`(최신순)였고, 문서끼리도 어긋나 있었다 — `10_MVP_기능범위.md`는 오름차순, `08`·`06`은 DESC. 범위를 물으니 결정은 "Collection 목록·Collection 내부 Record·Context 셋 다 오래된순 기본, 최신순도 지원"으로 확정됐다(2026-08-03).

"최신순도 지원"의 성격이 결정 지점이다. 사용자에게 노출하는 정렬 토글이 아니다 — **오래된순이 UI/UX상 나은지 화면을 보고 판단할 예정이라, 아니면 빠르게 뒤집기 위한 스위치**다. 스위치를 어디에 두느냐로 세 안이 갈렸다.

## 선택지

| 안 | 장점 | 단점 |
|---|---|---|
| (a) back 설정값 (`application.yml`) | API 표면이 안 늘어난다. 커서-방향 불일치가 구조적으로 불가능 | 뒤집기가 back 배포에 묶인다 — 프론트가 화면 보고 판단하는 흐름과 주체가 어긋난다 |
| (b) ASC 하드코딩 | 지금 코드가 제일 적다 | 뒤집을 때 JPQL의 `order by`와 커서 부등호 두 군데씩 × 6개 쿼리를 급하게 고치게 된다 — 한쪽만 뒤집으면 컴파일도 테스트도 통과한 채 목록이 조용히 어긋난다 |
| (c) 프론트가 상수로 고정해 보내는 파라미터 | 뒤집기가 프론트 상수 한 줄 + 프론트 배포. back은 초기 구현 후 관여 없음 | API 계약이 파라미터 3개만큼 늘고, 커서-방향 불일치 가능성이 계약상 생긴다(아래 보류) |

## 결정

**(c)를 고른다.** 능동적 선택이다.

결정적 이유: 뒤집기 판단의 주체가 프론트(화면 확인)이고, (c)만이 그 주체가 back 배포 사이클을 기다리지 않고 실행까지 할 수 있다. back 재배포 비용 자체는 크지 않지만, 판단 주체와 실행 주체를 일치시키는 값이 파라미터 3개의 표면 비용보다 크다고 봤다. 파라미터는 걷어내지 않고 유지한다 — 나중에 양방향이 다 필요한 상황이 생길 수 있다는 판단(2026-08-03)으로, "정책 확정 후 제거" 계획은 두지 않는다.

정한 계약:

| Endpoint | 파라미터 | 기본값 |
|---|---|---|
| `GET /v1/collections` | `sort` | `CREATED_AT_ASC` |
| `GET /v1/follows/{followId}/collections` | `sort` | `CREATED_AT_ASC` |
| `GET /v1/feed/collections/{id}/shelf` (8.1) | `sort` | `CREATED_AT_ASC` |
| `GET /v1/follows` (동봉 collections, 9.2) | `collectionSort` | `CREATED_AT_ASC` |
| `GET /v1/collections/{id}` | `recordSort` | `ADDED_AT_ASC` |
| `GET /v1/records/{recordId}` | `contextSort` | `CREATED_AT_ASC` |

- 8.1과 9.2 동봉 페이지는 티켓 본문에 명시되지 않았지만 같은 발행 Collection 조회·같은 커서 계약을 공유하므로 함께 간다 — 9.2 동봉 페이지의 커서를 9.3이 이어받는 구조라, 방향이 갈라지면 커서가 끊긴다. 9.2 쪽 이름이 `sort`가 아니라 `collectionSort`인 것은 중첩 축 접두어 규약(9.2의 `collectionSize`와 동일)이다.
- Collection 상세 안의 `records[].contexts`는 파라미터 없이 오름차순 고정 — 파라미터를 늘리지 않는다.
- Context 정렬 기준은 `origin_created_at` 그대로다(BD-25). 방향만 열린다.
- 정의되지 않은 값은 400 `INVALID_INPUT`. enum 바인딩 실패가 프레임워크 매핑으로 400이 된다.
- 인덱스는 그대로 둔다. btree 역방향 스캔이 ASC 조회를 받으므로 마이그레이션이 없다.

## 결과

- 이 결정으로 감수하는 것 — **커서-방향 불일치는 검증하지 않는다(보류).** 커서는 `Base64(정렬키,id)`로 방향 정보가 없다. DESC로 받은 커서를 ASC 요청에 넣으면 오류 없이 어긋난 페이지가 나간다(형식이 유효해 400을 낼 근거가 없다). 파라미터가 요청마다 변하지 않는 상수라는 전제 위에서만 안전한 구조다. 명세 1.4에 "커서는 발급받은 방향에서만 유효하다"를 규약으로 적었다.
- 재검토 트리거 — **정렬을 사용자 노출 토글로 만드는 순간.** 한 사용자가 페이지를 넘기다 방향을 바꿀 수 있게 되면 위 전제가 깨진다. 그 작업에는 커서에 방향을 싣고 서버가 불일치를 400으로 거절하는 변경이 **선행**돼야 한다. `Cursor`가 Feed에서 전혀 다른 의미(requestId, offset)로 공용되므로, 그때는 공용 레코드에 필드를 늘리지 말고 목록용 인코딩·디코딩 짝을 따로 두는 쪽을 권한다.
- 프론트가 상수를 바꿔 배포하는 순간, 이전 방향의 커서를 쥔 클라이언트는 한 번 어긋난 페이지를 받는다. 일회성이고 목록 재진입으로 사라져 별도 처리를 두지 않는다.
