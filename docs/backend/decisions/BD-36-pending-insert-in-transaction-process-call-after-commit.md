# BD-36. PENDING INSERT는 Core 트랜잭션 안에, `process` 호출은 커밋 이후 비동기로

- **상태**: Accepted
- **날짜**: 2026-07-29
- **관련**: S15P11A705-102, [back#61](https://github.com/Team-PinLog/back/issues/61),
  [BI-22](../implements/BI-22-2026-07-29-context-ai-enqueue.md),
  [BD-35](BD-35-ai-derived-invalidation-inside-deletion-transaction.md)(back#80, 삭제 방향),
  AI 파트 소유 명세 `docs/ai/spec/context-state-sync.md` §2·§3·§5·§8,
  `docs/ai/spec/ai-integration.md` §4~§6,
  공용 계약 `Team-PinLog/docs` `static/05_AI_설계.md` §6.4·§13.1

## 맥락

Context가 생겨도 `ai.context_ai_state`에 행이 없었다. AI 워커는 처리 대상 목록을 이 테이블에서
얻으므로, 행이 없으면 그 Context가 존재한다는 사실 자체를 모른다 — 임베딩도 키워드도 만들어지지
않는다. 시연 5단계 중 ① 맥락 저장과 ② 자연어 검색이 여기서 막힌다.

빠진 것은 두 가지이고 **둘의 순서가 계약이다.**

```text
① ai.context_ai_state 에 PENDING 행 INSERT
② POST /internal/v1/context/process 호출
```

②가 먼저 나가면 워커는 상태 행을 찾지 못한다. 그리고 그것으로 충분하지 않다 — **①이 커밋되기
전에 ②가 나가도 똑같이 실패한다.** 워커는 별 프로세스라 우리 트랜잭션의 미커밋 스냅샷을 볼 수
없다. 202를 받고도 아무 일도 일어나지 않고, 우리 로그에는 "정상 접수"만 남는다.

## 선택지

### 가. PENDING INSERT를 어디에 둘 것인가

| 안 | 장점 | 단점 |
|---|---|---|
| (a) Core 트랜잭션 안 | Core 데이터와 PENDING이 항상 함께 존재한다 | 백엔드가 타 파트 스키마에 쓴다 |
| (b) 커밋 후 별 트랜잭션 | 스키마 경계가 코드에서도 깨끗하다 | "Record는 저장됐는데 AI State가 없어 영원히 처리되지 않는 Context"가 생긴다. 재스캔도 이 행이 있어야 후보로 잡으므로 복구 경로가 없다 |
| (c) Outbox 테이블 | 유실이 구조적으로 없다 | `core`와 `ai`가 같은 인스턴스라 애초에 필요 없는 장치다 |

### 나. `process` 호출을 어디서 할 것인가

| 안 | 장점 | 단점 |
|---|---|---|
| (a) `@TransactionalEventListener(AFTER_COMMIT)` + `@Async` | 커밋 이후가 타입으로 보장된다. 롤백 시 호출 자체가 없다. 응답 지연이 사용자 요청에서 빠진다 | 호출이 별 스레드라 traceId가 끊긴다 |
| (b) 같은 트랜잭션 안에서 동기 호출 | 코드가 짧다 | **워커가 미커밋 행을 못 본다.** 외부 호출 지연만큼 커넥션·행 잠금이 유지되고, 호출 실패가 Record 저장을 롤백시킨다 |
| (c) 서비스 메서드 뒤에서 트랜잭션을 수동으로 나눠 호출 | 프레임워크 장치가 없다 | 호출 지점이 늘 때마다 "커밋 뒤인가"를 사람이 매번 확인해야 한다. 규칙이 코드가 아니라 관습이 된다 |

## 결정

**가-(a) + 나-(a).** 명세 `context-state-sync.md` §2·§3.1과 `ai-integration.md` §4가 지시하는
조합이며, 근거는 `core`와 `ai`가 같은 PostgreSQL 인스턴스의 서로 다른 스키마라는 사실이다.
단일 로컬 트랜잭션으로 묶이므로 분산 트랜잭션도 Outbox도 필요하지 않다.

핵심은 **순서를 관습이 아니라 트랜잭션 경계로 강제한 것**이다. 서비스는 PENDING INSERT와 이벤트
발행만 하고 호출은 하지 않는다. 호출은 `AFTER_COMMIT` 리스너에만 있으므로, 새 Context 생성 지점이
늘어도 "커밋 뒤에 부르는 것을 기억해야 하는" 부담이 생기지 않는다. 나-(c)를 버린 이유가 이것이다.

이벤트에는 엔티티 대신 식별자만 싣고 리스너가 본문을 다시 읽는다. 명세 §4.4가 "같은 `context_id`로
다른 `text`를 보내는 것은 계약 위반"이라고 못 박는데, 다른 곳에서 넘어온 문자열을 그대로 실으면
그 계약을 코드로 보장할 방법이 없다. Core 본문을 조회해 채우면 위반이 구조적으로 불가능해진다.

**호출 실패는 전부 삼킨다.** 삭제 방향(BD-35)이 "무효화 실패가 삭제를 롤백한다"를 감수한 것과
반대 방향의 선택인데, 대상이 다르기 때문이다. BD-35의 UPDATE는 **DB 쓰기**이고 실패하면 정합성이
깨진다. 여기의 실패는 **외부 서버 호출**이고, PENDING이 이미 커밋돼 있어 재스캔이 같은 Context를
다시 집는다. 유실이 아닌 것을 롤백하면 상대 서버 장애 때문에 사용자의 기록이 사라진다.

같은 이유로 상태를 `FAILED`로 바꾸지 않고 `retry_count`도 올리지 않는다. 호출 실패는 FastAPI
내부 작업의 실패가 아니며, 두 주체가 같은 사유로 `FAILED`를 각각 기록하면 원인 추적이 불가능해진다
(명세 §8).

### 왜 `ContextAiStateRepository`가 `AiDerivedDataRepository`와 별개인가

같은 테이블을 쓰는 클래스가 둘이 됐다. 합치는 편이 자연스럽지만 지금은 나누는 쪽을 택했다.

- back#80(`AiDerivedDataRepository`)이 **아직 병합되지 않았다.** `dev`를 base로 하는 이 PR이 같은
  파일에 메서드를 더하면 add/add 충돌이 되어, 두 PR 중 뒤에 가는 쪽이 반드시 손으로 푼다.
- 생성과 삭제는 **호출 시점과 트랜잭션 경계가 다르다.** 생성은 Core 저장과 같은 트랜잭션에서 한 번,
  삭제는 삭제 트랜잭션에서 벌크로 돈다.

back#80이 병합된 뒤 하나로 합칠지는 그때 판단한다. 합치더라도 옮기는 것은 SQL 상수 하나와 메서드
하나뿐이다.

## 결과

- 이 결정으로 감수하는 것:
  - **traceId가 호출 경계에서 끊긴다.** `@Async` 스레드에는 MDC가 넘어가지 않아 `X-Request-Id`가
    새 UUID가 된다. 우리 로그와 FastAPI 로그는 그 값으로 이어지지만, 사용자 요청 하나를 끝까지
    따라가려면 로그 두 구간을 사람이 이어야 한다.
  - **큐가 차면 호출이 조용히 버려진다.** `CallerRunsPolicy`를 쓰면 요청 스레드가 외부 호출을 대신
    수행해 FastAPI 장애가 그대로 Core 처리량 저하가 되므로 버리는 쪽을 택했다. 버려진 요청은
    PENDING으로 남아 재스캔 대상이 되므로 유실은 아니지만, **재스캔이 붙기 전까지는 실질적으로
    유실이다.** 재스캔 Scheduler(별건)가 이 결정의 전제다.
  - **백엔드가 타 파트 스키마에 쓴다.** BD-35와 같은 결합이며 같은 방식으로 표면을 좁혔다 — SQL
    상수 하나, 메서드 하나.
  - **호출 지점이 하나뿐이라는 보장은 코드가 아니라 리뷰다.** 누군가 서비스에서 직접
    `AiProcessClient`를 부르면 이 설계가 무너진다. 그 경로를 막는 장치는 두지 않았다.
- 재검토 트리거:
  - `ai` 스키마가 별도 인스턴스로 분리될 때. "동일 인스턴스"가 가-(a)의 전제다.
  - `process` 호출량이 전용 풀(core 2 / max 4 / queue 100)을 넘길 때. 지금 상한은 Context 생성
    빈도를 기준으로 잡은 값이라 근거가 약하다.
  - back#80 병합 후 — 두 리포지토리를 합칠지 판단한다.
