# BD-04. 목록은 커서 기반 `CursorPage<T>` + 불투명 커서로 페이지네이션한다

- **상태**: Accepted
- **날짜**: 2026-07-27
- **관련**: S15P11A705-42 (`377d006`, `14888f2`, `72b2899`), [BI-04](../implements/BI-04-2026-07-27-cursor-pagination.md)

## 맥락

`docs/development/api-conventions.md`는 이미 "목록 pagination은 커서 기반이며 `cursor`·`size` 쿼리 파라미터를 쓴다"고 정해 두었지만(공용 명세 `Team-PinLog/docs` `static/08_API_명세.md` §1.4), 이를 구현할 공용 타입이 없었다. 각 도메인이 커서 인코딩과 페이지 응답 형태를 각자 만들면 인코딩 방식(무엇을 담는지, 구분자, Base64 변형)과 응답 필드가 도메인마다 갈릴 위험이 있다. §1.4는 offset(`page`) 방식 대신 커서를 요구하는데, 그 이유는 이 서비스의 목록(피드·기록 등)이 삽입·삭제가 잦아 offset 기준이 흔들리기 때문이다.

## 선택지

| 안 | 장점 | 단점 |
|---|---|---|
| (a) offset(`page`/`size`) | 구현이 쉽고 `totalElements`(총 개수)를 함께 줄 수 있어 "n페이지 중 m" 같은 UI를 만들기 쉽다 | 조회 도중 목록에 삽입·삭제가 일어나면 같은 offset이 다른 항목을 가리켜 항목 누락·중복이 생긴다. 명세가 이미 커서를 택했다 |
| (b) 정렬키만 담는 커서(`Base64(정렬키)`) | 커서가 더 짧고 단순하다 | 정렬키가 동일한 두 행(같은 타임스탬프 등)이 있으면 그 사이에서 다음 페이지 시작점이 안정적으로 정해지지 않아 항목이 누락되거나 중복될 수 있다 |
| (c) **채택**: `Base64(정렬키,id)` 불투명 커서 + `CursorPage<T>` | 정렬키가 같아도 `id`가 유일하므로 (정렬키, id) 튜플이 전체 순서를 항상 확정한다. 커서가 공용 타입이라 도메인마다 인코딩이 갈리지 않는다 | 커서에 담긴 정렬키·id가 노출되므로 "불투명"을 계약으로 강제해야 한다(클라이언트가 파싱하면 안 됨) |
| (d) 서버 상한 없이 클라이언트가 준 `size`를 그대로 사용 | 명세 §1.4는 상한을 명시하지 않으므로 명세를 문자 그대로 따르는 선택 | 매우 큰 `size`를 요청하면 한 번의 조회로 DB와 메모리가 과도하게 부담을 진다 |

## 결정

**(c) + 서버 방어 상한**을 채택한다. 목록은 커서 기반 `CursorPage<T>` + `Base64(정렬키,id)` 불투명 커서를 쓴다. `size`는 기본 20, 방어 상한 100.

- **id를 tie-breaker로 담는 이유**: 정렬키 하나만으로는 동률(같은 시각 등)에서 다음 페이지 시작점을 확정할 수 없다. 기본키(`id`)는 유일하고 단조 증가하므로, `(정렬키, id)`를 튜플로 비교하면 동률이 있어도 순서가 항상 하나로 정해진다. 그래서 커서는 정렬키뿐 아니라 `id`를 반드시 함께 담는다.
- **서버 상한을 두는 이유**: 명세 §1.4 자체는 `size` 상한을 강제하지 않지만, 클라이언트가 비정상적으로 큰 `size`를 보내면 한 요청이 DB 조회량과 응답 페이로드를 과도하게 키운다. 명세를 어기지 않으면서 서버를 보호하기 위해, 클라이언트가 요청하지 않아도 항상 적용되는 내부 방어 상한(100)을 `CursorPage.normalizeSize`에 둔다. 이 상한은 명세 위반이 아니라 명세가 규정하지 않은 영역에 대한 서버 쪽 보수적 기본값이다.

## 결과

- 이 결정으로 감수하는 것: 커서에 정렬키 원문이 (Base64로 인코딩되어) 실려 있어 완전한 블랙박스는 아니다. 클라이언트가 디코딩해 파싱하면 다음 배포에서 정렬키 형식이 바뀔 때 깨질 수 있으므로, "클라이언트는 해석하지 않는다"를 계약으로 문서화했다(`api-conventions.md`). `totalElements`(총 개수)는 제공하지 않는다 — offset 방식이 주는 이점을 명시적으로 포기했다.
- 명세 충돌의 의도적 해소: 공용 명세 §1.6은 null 필드를 응답 직렬화에서 생략하는 것을 일반 규칙으로 둔다. `CursorPage.nextCursor`는 이 일반 규칙을 따르지 않고 `@JsonInclude`를 붙이지 않아 마지막 페이지에서도 명시적 `null`로 직렬화되도록 했다 — §1.4가 예시로 보여주는 `"opaque-cursor-or-null"` 형태를 지키기 위해 §1.6의 일반 규칙을 이 한 필드에 한해 의도적으로 적용하지 않은 것이다.
- 도메인 사용 방식: 각 도메인은 쿼리에서 `(정렬키, id)` 튜플 비교(예: `WHERE (sort_key, id) < (:sortKey, :id)`)로 다음 페이지를 가져오고, 결과를 `CursorPage.of(items, nextCursor)`(다음 페이지 있음) 또는 `CursorPage.last(items)`(없음)로 감싸 반환한다. 커서 생성·해석은 각 도메인이 직접 만들지 않고 `Cursor.encode`/`Cursor.decode`만 쓴다.
- 재검토 트리거: 어떤 도메인이 실제로 `totalElements`가 꼭 필요한 UI(예: "총 n건 중")를 요구할 때, 또는 서버 상한 100이 실사용 트래픽에서 너무 낮거나(정상 요청이 계속 잘림) 너무 높다는(과부하 사례) 근거가 나올 때.
