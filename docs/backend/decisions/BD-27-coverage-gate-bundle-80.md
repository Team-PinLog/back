# BD-27. 커버리지 게이트를 BUNDLE 기준 LINE·BRANCH 80%로 둔다

- **상태**: Accepted
- **날짜**: 2026-07-28
- **관련**: Jira 작업

## 맥락

`jacoco` 플러그인은 있었지만 `jacocoTestCoverageVerification`이 설정되지 않아, 커버리지가 얼마로 떨어져도 빌드가 통과했다. `check`가 끌고 가는 것은 리포트 생성(`jacocoTestReport`)뿐이었고 판정이 없었다. 즉 커버리지는 **관측만 되고 강제되지 않는 상태**였다.

이 시점에 하한선을 걸기로 한 이유는 지금 수치가 충분히 높아서다. 게이트를 넣어도 당장 고칠 것이 생기지 않고, 앞으로의 하락만 막는다.

```text
BUNDLE  LINE   787/799 = 98.5%
BUNDLE  BRANCH 183/212 = 86.3%
```

## 선택지

기준을 **어느 단위(element)** 에 걸지가 실질이었다. JaCoCo는 같은 80%를 BUNDLE(전체 합계)에 걸 때와 CLASS(클래스별)에 걸 때 완전히 다르게 판정한다.

| 안 | 장점 | 단점 |
|---|---|---|
| **(a) BUNDLE · LINE 80% + BRANCH 80%** | 지금 그대로 통과. 큰 하락을 잡는다. LINE만으로는 놓치는 분기 하락도 본다 | 개별 클래스가 낮아도 합계가 넘으면 통과한다 |
| (b) BUNDLE · LINE 80%만 | 가장 단순 | 여유가 18.5pp라 사실상 허수비다. 분기 커버리지 하락을 감지하지 못한다 |
| (c) CLASS · 80% | 가장 엄격. 약한 클래스를 직접 잡는다 | 지금 당장 4개가 실패한다 — `PinlogBackApplication`(LINE 33.3%), `Collection`(BRANCH 50%), `ApiResponseOpenApiCustomizer`(BRANCH 62.5%), `ApiResponseBodyAdvice`(BRANCH 75%). 게이트 도입과 테스트 보강이 한 티켓에 섞인다 |
| (d) 현재 수치를 그대로 하한선으로(LINE 98% · BRANCH 86%) | 하락을 즉시 잡는다 | 1~2줄의 정당한 리팩터링에도 빌드가 깨진다. 게이트를 낮추는 커밋이 일상이 되면 하한선의 의미가 사라진다 |

## 결정

**(a)를 채택한다. 능동적 선택.**

BUNDLE을 고른 이유는 이 티켓의 목적이 **하한선을 세우는 것**이고 테스트 보강이 아니기 때문이다. (c)는 커버리지가 낮은 클래스 4개를 지금 손보게 만들어 두 가지 일을 한 PR에 섞는다. 게이트를 먼저 세우고, 클래스별로 조이는 것은 별도로 판단하는 편이 되돌리기 쉽다.

LINE만 걸지 않고 BRANCH를 함께 건 이유는 **두 지표의 여유가 크게 다르다**는 실측이다. LINE은 98.5%로 18.5pp 여유가 있어 웬만한 하락에 반응하지 않는데, BRANCH는 86.3%로 6.3pp 여유다. 실제로 작동할 게이트는 BRANCH 쪽이고, LINE은 대규모 붕괴를 잡는 이중 안전장치로 남는다.

`PinlogBackApplication`은 집계에서 제외한다. `main()` 한 줄이라 테스트가 밟을 수 없고, 남겨두면 하한선을 올릴 때마다 이 클래스가 먼저 걸린다. 제외는 `JacocoReportBase`를 상속하는 모든 태스크에 같은 목록으로 적용해, **리포트에 보이는 수치와 게이트가 판정하는 수치가 같도록** 했다. 이 둘이 갈라지면 "리포트는 통과인데 빌드는 실패"가 나온다.

## 결과

**감수하는 것**

- **개별 클래스의 낮은 커버리지는 잡히지 않는다.** `Collection`의 BRANCH 50%, `ApiResponseOpenApiCustomizer`의 62.5%는 합계에 묻혀 통과한다. 이 게이트는 "전체가 무너지는 것"만 막고 "특정 클래스가 약한 것"은 막지 못한다.
- **LINE 기준은 당분간 유휴 상태다.** 98.5%에서 80%까지 떨어지려면 대규모 삭제가 필요하다. 실효는 BRANCH 쪽에서만 기대한다.
- **비율 기준은 원인을 구분하지 못한다.** 테스트를 지워서 떨어진 것과 테스트 없는 코드를 늘려서 떨어진 것이 같은 신호로 보인다. 어느 쪽인지는 리포트를 열어야 안다.
- **제외 목록이 늘어나면 게이트가 조용히 무력해진다.** 지금은 1개다. 커버리지가 낮은 클래스를 제외로 해결하기 시작하면 수치는 유지되면서 실제 보호는 사라진다.
- **로컬에서 `check`가 느려진다.** 검증이 `test` 결과에 의존하므로 Testcontainers 실행이 전제된다(실측 `clean check` 1m 16s). 검증 자체의 비용은 무시할 수준이다.

**재검토 트리거**

- BRANCH가 80%에 근접하면 → 기준을 올릴지, CLASS 단위로 옮길지 그때 판단한다. 임계값을 낮추는 것은 선택지에 두지 않는다.
- 제외 목록이 2개 이상으로 늘어나면 → 왜 테스트 불가인지 항목마다 확인한다. 테스트 가능한 코드를 제외로 넘기고 있다면 이 게이트는 이미 무의미하다.
- 개별 클래스의 낮은 분기 커버리지가 실제 결함으로 이어지면 → (c) CLASS element를 도입하고, 그때 예외가 필요한 클래스를 명시한다.
