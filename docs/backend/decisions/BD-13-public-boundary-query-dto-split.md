# BD-13. 공개 경계를 쿼리·DTO 분리로 강제 — 403 대신 404

- **공용 계약**: [06_데이터모델_및_무결성 §5](https://github.com/Team-PinLog/docs/blob/main/static/06_데이터모델_및_무결성.md) · [08_API_명세 §1.2](https://github.com/Team-PinLog/docs/blob/main/static/08_API_명세.md)

## 맥락

`context.body`는 사용자가 장소를 저장한 개인적 이유이며 **타인에게 절대 공개되지 않는다.** 반면 Place·Keyword·Record 생성일은 공개된다. 같은 테이블에서 소유자에게는 전부, 타인에게는 일부만 내보내야 한다.

이런 구조에서 사고는 "막는 것을 깜빡해서" 난다. 그래서 **실수했을 때 어느 방향으로 실패하는가**가 선택 기준이 되었다.

## 선택지

| 안 | 실수했을 때 |
|---|---|
| (a) 단일 쿼리로 다 읽고 응답 조립에서 필드를 걸러낸다 | **개인정보 유출.** 필터를 빠뜨리면 본문이 그대로 나간다 |
| (b) 공개용 복제 테이블을 만든다 | **낡은 데이터 노출.** 동기화를 놓치면 삭제된 내용이 계속 보인다 |
| **(c) 조회 쿼리와 DTO를 아예 분리한다** | **컴파일 오류 또는 null.** 필드가 존재하지 않아 실수가 코드 단계에서 드러난다 |

## 결정

**(c)를 채택한다. 능동적 선택.** 실패가 안전한 방향으로 나도록 **조회 단계에서 분리**한다.

- **저장은 한 벌로 유지한다.** 공개용 복제본을 만들지 않는다. 이미 `ai.context_keyword`가 마스킹된 파생본 역할을 한다([BD-18](BD-18-keyword-preset-and-visibility.md)).
- **쿼리 분리** — 타인 조회용 쿼리는 `context.body`를 아예 `SELECT`하지 않는다. 리포지토리 메서드명에 `ForOwner` / `Public`을 명시한다.
- **DTO 분리** — 소유자용과 공개용 응답 클래스를 **상속 없이 별개로** 정의한다. 상속이나 조건부 직렬화는 부모에 필드가 추가될 때 조용히 노출된다.
- **경로 통합** — 타인이 데이터에 접근하는 경로는 Feed, Collection 상세, 팔로우한 Shelf 셋뿐이다. 이 셋이 단일 공개 조회 서비스를 거치게 해 노출 필드를 한 곳에서 관리한다.

**권한 실패는 403이 아니라 404다.** 403은 "그 리소스가 존재하기는 한다"를 알려준다. 익명 서비스에서는 존재 여부 자체가 정보다. 타인의 개인 Record 조회, 타인의 Context·Collection 수정·삭제, 보유하지 않은 `followId` 조회가 모두 404다.

진입 전 권한 검사는 `is_published = true`, `deleted_at IS NULL`, 소유자 미탈퇴 셋이다.

## 결과

**감수하는 것**

- **쿼리와 DTO가 중복된다.** 같은 리소스에 대해 두 벌을 유지해야 하고, 공통 필드가 바뀌면 양쪽을 고쳐야 한다. 이 중복은 의도된 비용이다 — 공유하는 순간 (a)로 되돌아간다.
- **상속 금지로 보일러플레이트가 는다.** 매퍼도 두 벌이다.
- **404가 디버깅을 어렵게 한다.** 개발 중에도 "권한이 없는 건지 진짜 없는 건지" 응답만으로 구분되지 않는다. 로그에서 `traceId`로 확인해야 한다([BD-03](BD-03-api-response-envelope.md)).
- **경로 통합이 규율에 의존한다.** 새 공개 경로를 만들 때 단일 서비스를 우회하면 경계가 무너진다. 컴파일러가 막아주지 않는 유일한 지점이다.

**재검토 트리거**

- 타인 접근 경로가 셋을 넘어 늘어나면 → 단일 공개 조회 서비스가 실제로 모든 경로를 덮고 있는지 재점검한다.
- Keyword가 프리셋 밖에서 자유 생성되도록 바뀌면 → 공개 안전성의 전제가 깨진다. [BD-18](BD-18-keyword-preset-and-visibility.md)과 **반드시 함께** 재검토한다.
