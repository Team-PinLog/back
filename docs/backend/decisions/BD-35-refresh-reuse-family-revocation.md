# BD-35. Refresh 재사용을 유출로 간주해 그 회원의 세션을 전부 폐기한다

- **상태**: Accepted
- **날짜**: 2026-07-29
- **관련**: S15P11A705-131 · [back#78](https://github.com/Team-PinLog/back/issues/78) · [BD-32](BD-32-refresh-reuse-no-family-revocation.md)(이 결정이 대체) · [BD-21](BD-21-auth-token-model.md)(토큰 모델) · [BI-21](../implements/BI-21-2026-07-29-refresh-reuse-family-revocation.md)

## 맥락

[BD-32](BD-32-refresh-reuse-no-family-revocation.md)가 재사용 감지 시 계열 폐기를 **미뤘다.** 근거는 위험의 크기가 아니라 PR 크기였고, "이 PR이 병합되는 즉시 후속 티켓으로 올린다"는 트리거를 걸어 뒀다. 그 PR([back#73](https://github.com/Team-PinLog/back/pull/73))이 2026-07-29에 병합됐다.

BD-32가 감수 사항으로 적어 둔 구멍은 그대로였다 — Refresh가 유출되면 공격자가 먼저 회전해 새 토큰을 얻고, 정상 사용자만 401로 끊긴다. **공격자 세션은 최대 7일 살아남는다.** [RFC 9700 §4.14.2](https://www.rfc-editor.org/rfc/rfc9700.html)가 재사용 감지 시 그 사용자의 refresh를 전부 폐기하라고 하는 이유다.

한편 폐기를 구현하려면 회원 단위로 `jti`를 모아 볼 수단이 필요하다. `RefreshTokenStore`는 세션 독립성을 위해 `jti`마다 키를 하나 두므로([BD-21](BD-21-auth-token-model.md)) 회원 단위 조회 경로가 없다.

## 선택지

폐기를 **할지**는 BD-32가 이미 "해야 한다"로 결론 냈으므로, 남은 선택은 **무엇을 폐기 대상에 넣는가**와 **어떻게 모으는가**였다.

| 안 | 장점 | 단점 |
|---|---|---|
| (a) 재사용된 `jti`만 폐기 | 오탐이 없다 | 지금과 같다. 공격자가 회전해 받은 토큰이 살아남아 구멍이 닫히지 않는다 |
| **(b) 그 회원의 Refresh 전부 폐기** | 유출 시 공격자 세션이 즉시 끊긴다. RFC 권고를 충족한다 | **오탐 시 전체 로그아웃.** 클라이언트가 같은 토큰을 두 번 보내기만 해도 모든 기기에서 끊긴다 |
| (c) 재사용된 계열만 폐기(토큰마다 계열 id 부여) | 오탐 범위가 한 기기로 좁아진다 | 계열 id를 토큰에 넣고 이어붙이는 구조가 추가된다. 그런데 **공격자가 어느 계열에 있는지 서버는 모른다** — 유출된 토큰과 정상 토큰이 같은 계열이라 좁히는 의미가 없다 |

수집 방법은 BD-32가 이미 (b) `SCAN`을 기각했다(키 공간에 비례, 운영 Redis 비권장). 남은 것은 회원별 인덱스를 두는 것이다.

## 결정

**(b) — 능동적 선택.** 회원별 `jti` 인덱스(`auth:refresh-index:<memberId>` Set)를 두고, 재사용 감지 시 그 회원의 Refresh를 전부 삭제한다.

결정적 이유는 **서버가 재사용과 유출을 구별할 수 없다**는 것이다. 같은 `jti`가 두 번 들어온 사실만 관측되고, 그것이 버그 있는 클라이언트인지 탈취인지 알 방법이 없다. 구별할 수 없을 때는 **더 나쁜 쪽을 가정**한다 — 오탐의 대가는 재로그인이고, 미탐의 대가는 공격자가 7일간 계정을 쓰는 것이다. 비대칭이 크다.

(c)를 기각한 이유가 이 결정의 핵심이다. 계열을 좁혀도 **유출된 토큰이 정상 사용자와 같은 계열에 있으므로** 공격자만 골라 끊을 수 없다. 좁히기의 이득은 오탐 범위뿐인데, 그 대가로 토큰에 계열 id를 넣고 회전마다 이어붙이는 구조를 진다. 오탐은 아래 방어선으로 이미 낮다.

## 결과

**이 결정으로 감수하는 것**

- **오탐 시 전체 로그아웃.** 클라이언트가 같은 Refresh를 동시에 두 번 보내면 재사용으로 판정돼 모든 기기에서 끊긴다. 방어선은 공용 계약이다 — [08 §3.3](https://github.com/Team-PinLog/docs/blob/main/static/08_API_명세.md)이 "재발급 요청은 **동시에 하나만** 보낸다. 401이 여러 건 동시에 발생해도 재발급은 한 번만 호출하고 나머지 요청은 그 결과를 기다린다"를 이미 명시하고 있다. 이 계약을 지키지 않는 클라이언트는 이제 로그아웃으로 처벌받는다.
- **발급마다 Redis 연산이 하나 늘어난다**(`SADD` + `EXPIRE`). 로그인·회전 경로에만 붙고 검증 경로에는 없다.
- **인덱스에 만료된 `jti`가 잠시 남는다.** 토큰 키는 TTL로 사라지지만 Set 원소는 소비 시점에만 빠진다. 없는 키를 지우는 것은 무해하고, Set 자체도 TTL을 갖는다.
- **폐기는 Redis에 의존한다.** Redis가 죽으면 폐기도 안 된다 — 다만 그 상태에서는 재발급 자체가 불가능하므로 새 구멍은 아니다.

**재검토 트리거**

- 오탐이 실제로 관측되면(정상 사용자가 이유 없이 전체 로그아웃되는 문의) (c)를 다시 본다. 그때는 계열 id의 비용을 낼 가치가 생긴다.
- 회원 탈퇴([S15P11A705-65](https://ssafy.atlassian.net/browse/S15P11A705-65))가 같은 `revokeAll`을 쓴다. 두 호출자가 생기면 이 연산의 위치(`RefreshTokenStore`)가 맞는지 다시 본다.
- 다중 기기 세션 관리 UI("다른 기기에서 로그아웃")가 생기면 인덱스를 조회용으로도 쓰게 된다. 지금은 폐기 전용이다.
