# BD-21. 인증 토큰 모델 — JWT Access 30분 / Refresh 7일, Refresh는 Redis

- **상태**: Accepted
- **날짜**: 2026-07-24 (API 명세 §1.1 확립 시점. 정확한 커밋 특정 불가)
- **작성 시점**: 2026-07-27 — 결정 이후에 정리
- **관련**: S15P11A705-76
- **공용 계약**: [08_API_명세 §1.1](https://github.com/Team-PinLog/docs/blob/main/static/08_API_명세.md) · [02_정책_정의서 §2](https://github.com/Team-PinLog/docs/blob/main/static/02_정책_정의서.md)

## 맥락

MVP 로그인은 Google·Kakao·Naver 소셜 로그인만 제공하고 자체 비밀번호 로그인은 없다. 소셜 콜백 이후 서비스 세션을 어떻게 유지할지 정해야 했다.

핵심 제약은 **JWT는 자체적으로 폐기되지 않는다**는 것이다. 서명이 유효하고 만료 전이면 서버가 거부할 방법이 토큰 자체에는 없다. 로그아웃과 탈퇴는 즉시 반영되어야 한다.

## 선택지

| 안 | 장점 | 단점 |
|---|---|---|
| (a) 서버 세션(쿠키 + 세션 저장소) | 무효화가 자연스럽고 구현이 단순 | 상태를 서버가 들고 있어 수평 확장 시 세션 공유가 필요. 모바일 웹·앱 확장 시 쿠키 정책 문제 |
| (b) Access JWT 단독(장기 만료) | 저장소가 필요 없음 | 로그아웃·탈퇴를 즉시 반영할 수 없다. 탈취 시 만료까지 유효 |
| **(c) Access JWT(단기) + Refresh 토큰을 Redis에** | 무효화 지점이 Refresh 하나로 모임. TTL로 만료가 자동 정리됨 | Redis 의존이 인증 경로에 생긴다 |

## 결정

**(c)를 채택한다.**

**Redis에 Refresh를 두는 근거는 제약으로 주어졌다** — 공용 계약이 로그아웃 무효화, 회전 발급 관리, TTL 자동 만료를 요구한다([08 §1.1](https://github.com/Team-PinLog/docs/blob/main/static/08_API_명세.md)). Redis는 Feed Cache 용도로 이미 도입되어 있어 새 인프라가 늘지 않는다.

**만료 수치 30분 / 7일은 기본값 수용이다.** 널리 쓰이는 값을 그대로 채택했고, 이 서비스의 위협 모델이나 사용 패턴에서 도출한 값이 아니다. 바꿀 이유를 찾지 못해 유지한다.

함께 확정한 것:

- 보호 Endpoint는 `Authorization: Bearer {accessToken}`을 요구한다.
- **개인 API에서 사용자 ID를 Query나 Body로 받지 않는다.** 서버가 토큰으로 식별한다. 내부 `member.id`는 공개 응답에 넣지 않는다([BD-14](BD-14-identifier-concealment.md)).
- Access 만료 시 401을 반환하고 클라이언트가 `POST /auth/refresh`로 재발급한다.

## 결과

**감수하는 것**

- **무효화 지연** — 로그아웃해도 이미 발급된 Access Token은 최대 30분간 유효하다. 즉시 차단이 필요하면 별도의 블랙리스트가 필요하다.
- **Redis 의존** — Redis 장애 시 재발급이 불가능해 세션이 30분 안에 모두 끊긴다. 인증 경로가 캐시 계층의 가용성에 묶인다.
- **수치의 근거 없음** — 30분/7일이 적정한지 검증한 바 없다. 짧으면 재발급 트래픽이, 길면 탈취 노출 시간이 늘어난다.

**재검토 트리거**

- 만료 수치는 근거 없이 채택했으므로, **실사용 데이터(재발급 빈도·세션 이탈)가 쌓이면 한 번은 검토해야 한다.** 기본값을 그대로 두는 것 자체가 결정임을 잊지 않기 위해 트리거로 남긴다.
- 즉시 로그아웃이 보안 요건이 되면 → Access 만료를 더 줄이거나 토큰 블랙리스트를 도입한다.
- Redis 장애가 인증 전체를 끊는 것이 허용되지 않으면 → Refresh 저장소를 영속 저장소로 옮기거나 Redis를 이중화한다.
