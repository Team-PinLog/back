# BD-22. 가입 확정 시점 — 약관 동의 전에는 `member`를 생성하지 않는다

- **상태**: Accepted
- **날짜**: 2026-07-24 (API 명세 §3.2~3.3 확립 시점. [06 §8](https://github.com/Team-PinLog/docs/blob/main/static/06_데이터모델_및_무결성.md)에 확정으로 기록됨)
- **작성 시점**: 2026-07-27 — 결정 이후에 정리
- **관련**: S15P11A705-76
- **공용 계약**: [08_API_명세 §3.2~3.3](https://github.com/Team-PinLog/docs/blob/main/static/08_API_명세.md) · [02_정책_정의서 §2](https://github.com/Team-PinLog/docs/blob/main/static/02_정책_정의서.md)

## 맥락

소셜 로그인 콜백이 돌아온 시점과 사용자가 필수 약관에 동의하는 시점 사이에 간극이 있다. 그 사이에 `member` 행을 만들 것인가가 문제였다.

최초 가입 시 안내하고 동의를 받아야 하는 항목이 있다 — Collection 생성 시 자동 발행, Context 원문 비공개, 공개 가능 정보의 범위, Shelf 단위 익명 Follow 구조. 동의 없이 서비스를 쓰게 할 수 없다.

## 선택지

| 안 | 장점 | 단점 |
|---|---|---|
| (a) 콜백에서 `member`를 만들고 `agreed` 플래그로 관리 | 이후 요청이 항상 실재하는 `member`를 가리킨다 | 동의하지 않고 이탈한 미완료 계정이 쌓인다. **모든 조회가 "가입했지만 동의 안 한" 상태를 걸러야 한다.** 소셜 계정 유니크도 미완료 행이 선점한다 |
| **(b) 콜백에서는 단기 가입 토큰만 발급하고, 동의 시점에 `member`·`social_account`를 생성** | 테이블에는 완결된 회원만 존재한다. 이탈하면 아무것도 남지 않는다 | 콜백과 동의 사이의 상태를 토큰으로 들고 있어야 한다 |

## 결정

**(b)를 채택한다. 능동적 선택.**

결정적인 이유는 **미완료 상태를 데이터 모델에서 없앤 것**이다. `member` 행이 존재한다는 것이 곧 "동의를 마친 회원"을 뜻하게 되어, 이후 모든 조회가 추가 조건 없이 돌아간다. [BD-10](BD-10-integrity-in-database.md)에서 `member`에 `status` 컬럼을 두지 않고 삭제 판정을 `deleted_at` 하나로 고정한 것과 같은 방향이다 — 상태를 늘리지 않는다.

```text
소셜 콜백 → 단기 가입 토큰 발급 (member 없음)
         → POST /me/agreements (동의)
         → member·social_account 생성
         → Access·Refresh 발급
```

## 결과

**감수하는 것**

- **콜백과 동의 사이의 상태를 토큰이 들고 있어야 한다.** 이 토큰은 짧게 살고, 탈취되면 타인 명의로 가입이 완료될 수 있으므로 만료를 짧게 유지해야 한다([BD-21](BD-21-auth-token-model.md)).
- **이탈하면 흔적이 없다.** 의도한 동작이지만, "몇 명이 동의 단계에서 이탈했는가"를 DB로는 알 수 없다.
- **동의 증빙 수단이 없다.** 동의를 받고 `member`를 만들지만 **약관 종류·버전·시각을 기록하지 않는다.** 정책이 요구하는 필수 동의를 나중에 증빙할 방법이 현재 없다. [06 §8](https://github.com/Team-PinLog/docs/blob/main/static/06_데이터모델_및_무결성.md)의 미확정 항목이다.

**재검토 트리거**

- 동의 증빙 요구가 생기면(약관 개정, 분쟁 대응) → 약관 동의 이력 테이블을 추가한다. 종류·버전·동의 시각이 필요하다. 이 결정 자체는 유지된다.
- 가입 단계 이탈률을 측정해야 하면 → DB가 아닌 이벤트 로그에서 얻는다. 미완료 `member`를 만드는 방향으로 되돌리지 않는다.
