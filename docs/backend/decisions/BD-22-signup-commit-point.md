# BD-22. 가입 확정 시점 — 소셜 인증 성공이 곧 가입 완료

- **상태**: Accepted
- **날짜**: 2026-07-27 (`Team-PinLog/docs` `d5288cd` 가입 흐름 변경)
- **작성 시점**: 2026-07-27 — 결정 이후에 정리
- **관련**: Jira 작업
- **공용 계약**: [11_인증_설계 §5.1·§6](https://github.com/Team-PinLog/docs/blob/main/static/11_인증_설계.md) · [08_API_명세 §3.2](https://github.com/Team-PinLog/docs/blob/main/static/08_API_명세.md) · [02_정책_정의서 §2](https://github.com/Team-PinLog/docs/blob/main/static/02_정책_정의서.md)

## 맥락

최초 가입 시 안내하고 동의를 받아야 하는 항목이 있다 — Collection 생성 시 자동 발행, Context 원문 비공개, 공개 가능 정보의 범위, Shelf 단위 익명 Follow 구조. 동의 없이 서비스를 쓰게 할 수 없다.

문제는 **동의를 어디서 받고, 그 사이 서버에 무엇을 남기는가**였다. 소셜 콜백이 돌아온 시점과 사용자가 동의하는 시점 사이에 간극이 생기면 서버에 "가입했지만 동의 안 한" 중간 상태가 필요해진다.

## 선택지

| 안 | 장점 | 단점 |
|---|---|---|
| (a) 콜백에서 `member`를 만들고 `agreed` 플래그로 관리 | 이후 요청이 항상 실재하는 `member`를 가리킨다 | 미완료 계정이 쌓이고 **모든 조회가 그 상태를 걸러야 한다.** 소셜 계정 유니크를 미완료 행이 선점한다 |
| (b) 콜백에서 단기 가입 토큰만 발급하고, 동의 API로 가입 확정 | 테이블에는 완결된 회원만 남는다 | 서버에 "가입 미완료" 중간 상태와 단기 토큰이 필요해 흐름이 복잡해진다. 동의 전용 Endpoint도 따로 유지해야 한다 |
| **(c) 약관을 로그인 시작 이전으로 옮기고, 소셜 인증 성공 시점에 즉시 생성** | 중간 상태 자체가 사라진다. 로그인과 가입이 같은 흐름이 된다 | 서버가 동의 여부를 받지도 저장하지도 않는다 |

## 결정

**(c)를 채택한다. 제약으로 주어짐** — 공용 계약이 정한 흐름이며, 백엔드는 콜백 트랜잭션의 책임만 진다.

```text
[클라이언트] 필수 약관 안내 — 진행하면 동의로 간주
   → 소셜 로그인 시작
   → 공급자 인증 성공
[서버]  활성 social_account 있으면 그 회원으로 로그인
        없으면 이 시점에 member·social_account 생성
   → 두 경우 모두 인증 쿠키 발급 후 클라이언트로 리다이렉트
```

**(b)가 한때 채택안이었다가 뒤집혔다.** 미완료 상태를 없애려는 목적은 같았지만, 단기 토큰으로 상태를 들고 있는 대신 **약관을 로그인 이전으로 옮겨 상태가 생길 여지 자체를 제거**하는 쪽이 단순하다고 결론났다([11_인증_설계 §6](https://github.com/Team-PinLog/docs/blob/main/static/11_인증_설계.md)). 그 결과 `POST /me/agreements`는 계약에서 사라졌다.

`member` 행이 존재한다는 것은 곧 "소셜 인증을 통과한 회원"을 뜻한다. [BD-10](BD-10-integrity-in-database.md)에서 `member`에 `status` 컬럼을 두지 않고 삭제 판정을 `deleted_at` 하나로 고정한 것과 같은 방향이다 — 상태를 늘리지 않는다.

## 결과

**감수하는 것**

- **동의 증빙 수단이 전혀 없다.** 서버는 동의 여부를 받지도 저장하지도 않는다. 약관 개정이나 분쟁 시 "동의를 받았다"를 서버 데이터로 증명할 수 없다. [06 §8](https://github.com/Team-PinLog/docs/blob/main/static/06_데이터모델_및_무결성.md)의 열린 항목이며, **이전 안(b)보다 증빙 관점에서는 후퇴한 선택이다.**
- **동의 시점 통제가 클라이언트에 있다.** 안내 화면을 건너뛰고 인증을 시작시키는 클라이언트가 있으면 서버는 알 수 없다.
- **이탈 측정 불가** — 안내 화면에서 이탈하면 인증이 시작되지 않아 아무 데이터도 남지 않는다. 의도한 동작이지만 이탈률을 DB로는 알 수 없다.

**재검토 트리거**

- 동의 증빙 요구가 생기면(약관 개정, 분쟁 대응) → **동의 종류·버전·시각을 서버가 받는 경로부터 신설해야 한다.** 이력 테이블만 추가해서는 해결되지 않는다. 현재는 서버로 오는 신호 자체가 없기 때문이다.
- 가입 단계 이탈률을 측정해야 하면 → DB가 아닌 클라이언트 이벤트 로그에서 얻는다. 미완료 `member`를 만드는 (a)로 되돌리지 않는다.
