# BD-07. 소프트 삭제 + 복구 없음 + 활성행 부분 유니크

- **상태**: Accepted
- **날짜**: 2026-07-22 (데이터 모델 확립 시점. 단일 커밋으로 특정 불가)
- **기록**: 소급 (2026-07-27 작성)
- **관련**: S15P11A705-76
- **공용 계약**: [06_데이터모델_및_무결성 §1.1·§3.1·§7](https://github.com/Team-PinLog/docs/blob/main/static/06_데이터모델_및_무결성.md) · [02_정책_정의서 §1.5](https://github.com/Team-PinLog/docs/blob/main/static/02_정책_정의서.md)

## 맥락

사용자 소유 데이터(Record·Context·Collection·Follow·회원)의 삭제 정책을 정해야 했다. 세 가지가 서로 얽혀 있어 따로 결정할 수 없었다.

1. 물리 삭제인가 소프트 삭제인가
2. 소프트 삭제라면 사용자에게 복구를 제공하는가
3. 유니크 제약을 전체에 걸 것인가 활성행에만 걸 것인가

2번이 3번을 강제한다. 복구를 제공하지 않으면 삭제 후 재저장은 항상 새 INSERT이고, 그러면 유니크는 반드시 활성행에만 걸려야 한다. 전체 유니크로 두면 재저장이 실패한다.

## 선택지

| 안 | 장점 | 단점 |
|---|---|---|
| (a) 하드 삭제 | 행이 늘지 않음. 유니크 제약이 단순 | 실수 삭제 복구 불가. 회고 서비스에서 데이터 소실이 치명적. 파생 데이터 정리 순서에 실패하면 되돌릴 수 없음 |
| (b) 소프트 삭제 + 사용자 복구 제공 | 실수 복구 가능 | 휴지통 UI·보존 기간·복구 시 유니크 충돌 처리가 모두 딸려옴. 리소스마다 복구 가능 여부가 갈리면 정책이 파편화 |
| **(c) 소프트 삭제 + 복구 없음** | 모든 리소스가 같은 규칙. 재저장 경로가 하나(새 INSERT)로 고정 | 삭제 행이 무한 증식. 모든 조회에 `deleted_at IS NULL` 필터가 필요하고 누락 시 곧바로 사고 |

## 결정

**(c)를 채택한다. 능동적 선택.**

결정적 이유는 **정책 통일성**이다. 리소스마다 복구 가능 여부가 다르면 사용자도 구현도 규칙을 기억할 수 없다. 모두 소프트 삭제하고 아무것도 복구하지 않는 하나의 규칙으로 두고, **특정 리소스에 복구 요구가 실제로 생기면 그때 그 리소스만 개별 결정**하기로 했다.

파생되는 강제 사항:

- 삭제 후 재저장은 기존 행의 재활성화가 아니라 **항상 새 INSERT**다.
- 따라서 모든 유니크 제약은 **활성행 부분 유니크**(`WHERE deleted_at IS NULL`)로 정의한다. 예외는 `place`뿐이며, Place는 공용 데이터라 삭제하지 않으므로 전체 유니크다([BD-18](BD-18-place-snapshot.md)).
- 운영자 복구도 `deleted_at`을 `null`로 되돌리지 않고 데이터를 읽어 새로 INSERT한다. 정책과 구현이 한 경로만 갖게 하기 위함이다.

AI 파생 데이터는 이 규칙에서 빠진다. 소프트 삭제하지 않고 즉시 파기한다([BD-15](BD-15-ai-derived-immediate-purge.md)).

## 결과

**감수하는 것**

- **필터 누락 위험** — 모든 조회에 `deleted_at IS NULL`이 필요하다. 누락하면 삭제된 데이터가 Feed에 노출되는 사고로 직결된다. Collection과 Follow도 대상이라는 점을 놓치기 쉽다.
- **무한 증식** — `collection_record`와 `follow`가 특히 빠르게 쌓인다. 보존 기간과 하드 삭제 배치 정책이 아직 없다([06 §8](https://github.com/Team-PinLog/docs/blob/main/static/06_데이터모델_및_무결성.md)).
- **사용자 기대** — 실수로 지운 기록을 되돌릴 수 없다. 삭제 확인 UX가 그만큼 중요해진다([BD-10](BD-10-minimum-holding-invariants.md)).

**재검토 트리거**

- 특정 리소스에 복구 요구가 생기면 → 전체 정책을 뒤집지 않고 **그 리소스만** 개별 결정한다. 이것이 이 결정에 내장된 확장 경로다.
- 삭제 행 누적이 조회 성능이나 저장 비용에 실제 영향을 주면 → 보존 기간과 하드 삭제 배치를 함께 결정한다. 이때 부분 유니크와 충돌하지 않는지 확인해야 한다.
