# BD-45. 작업 로그와 기록 목록을 공유 파일이 아니라 항목별 파일로 둔다

- **상태**: Accepted
- **날짜**: 2026-08-01
- **관련**: [back#133](https://github.com/Team-PinLog/back/issues/133)

## 맥락

작업 로그(`docs/backend/WORKLOG.md`)와 기록 3폴더·`spec`의 `README.md` 목록 표는 모두 **모든 작업이 파일 끝에 한 행을 더하는 구조**였다. 열린 PR이 둘 이상이면 같은 지점에서 반드시 충돌한다.

`.gitattributes`의 `merge=union`이 `WORKLOG.md` 하나에만 걸려 있었고, 그것도 **로컬 머지 드라이버라 GitHub 서버 병합에는 적용되지 않는다.** 그래서 `gh pr update-branch`는 WORKLOG를 건드리는 두 번째 PR부터 항상 실패했고, 우회는 로컬 병합뿐이었다. `dev` 보호 설정이 `strict: true`라 브랜치를 갱신할 때마다 `backend-ci`를 다시 기다린다 — 2026-07-31에 PR 4건을 묶어 머지하며 CI 7회(약 21분)와 수동 개입 3회가 들었다.

결정 시점에 확인한 사실:

- 공유 append 파일은 5개다. `WORKLOG.md`와 `decisions`·`implements`·`troubleshooting`·`spec`의 `README.md` 목록 표. **뒤의 넷은 `merge=union`조차 없다.** `spec`의 표는 그때까지 비어 있어 실제로 충돌한 적은 없었다 — 터지기 전에 잡힌 경우다.
- 기록 문서 84개 **전부**가 H1에 번호와 요약을, 헤더에 `- **상태**:`를 갖고 있다. 목록 표의 세 컬럼은 그 값을 손으로 옮겨 적은 사본이다.
- 그 사본은 이미 어긋나 있었다. `implements`는 `BI-22`를 빠뜨렸고, `troubleshooting`은 `BT-02`를 `⚠️ 미해결`로 적어뒀는데 문서는 `✅ 해결`이었다.
- `WORKLOG.md`를 읽는 CI·테스트·도구는 없다. 참조는 전부 문서 산문이다.

## 선택지

| 안 | 장점 | 단점 |
|---|---|---|
| (a) 항목별 파일로 쪼개고 목록 파일을 두지 않는다 | 공유 파일이 사라져 서버 병합 경로에서도 안전하다. 표 셀에 눌려 있던 산문이 읽히게 된다 | 한 파일을 열어 전부 보는 훑기가 없어진다 |
| (b) 나머지 넷에도 `merge=union`을 건다 | 변경이 한 줄이다 | **문제를 못 푼다.** union은 로컬 전용이라 `gh pr update-branch`는 그대로 실패한다 |
| (c) 목록을 CI가 생성한다 | 어긋남이 없어진다 | 생성된 파일도 공유 파일이라 충돌은 남는다. `dev` 직접 푸시가 막혀 있어 봇 커밋 경로도 없다 |
| (d) 로그 줄을 PR에서 빼고 머지 후 `dev`에 따로 커밋한다 | 파일 구조를 안 바꾼다 | 기록이 리뷰 대상에서 빠지고, 사람이 지키는 규칙이 되어 빠뜨리기 쉽다. 이 레포는 번호·인덱스 관리가 그 방식으로 이미 두 번 샜다 |

## 결정

**(a)를 고른다.** 능동적 선택이다.

결정적인 이유 둘:

1. **(b)와 (c)는 문제를 못 푼다.** 충돌의 원인은 union의 부재가 아니라 **공유 파일의 존재**다. 파일을 공유하는 한 서버 병합은 막힌다.
2. **목록 표는 원본이 아니라 사본이다.** `decisions/README.md`가 파트 간 합의를 두고 "같은 결정에 원본이 둘이 되면 반드시 어긋난다"고 적어둔 원칙을, 자기 목록 표가 어기고 있었다. 사본을 지우면 어긋날 것이 없어진다.

같이 정한 것:

- **인덱스 파일을 만들지 않는다.** 목록 파일을 두는 순간 같은 충돌이 되살아난다. 시간순은 파일명이 준다.
- **`WORKLOG.md`는 내용을 옮기지 않고 거기서 멈춘다.** 표 행은 이미 한 줄짜리라 쪼개도 정보가 늘지 않는다.
- **`merge=union` 지정과 주석을 지운다.** 멈춘 파일에는 발동할 일이 없고, 남겨두면 "WORKLOG는 append 전용 파일이다"라는 현재형 설명이 계속 틀린 말을 하며, 다음 사람이 "union이 있으니 공유 파일을 하나 더 만들어도 되겠다"고 읽을 여지를 남긴다.
- **`BD-##`·`BI-##`·`BT-##` 전역 번호는 그대로 둔다.** 아래 참고.

## 결과

**얻는 것.** 브랜치가 몇 개든 로그·기록 파일이 겹치지 않는다. `gh pr update-branch`가 서버에서 병합해도 막히지 않는다. `strict: true`와 곱해지던 CI 재실행 비용이 사라진다. 표 셀 안에 수천 자로 눌려 있던 산문이 파일로 펴져 diff가 읽힌다. `BI-22` 누락과 `BT-02` 오기가 함께 사라지고 같은 종류의 어긋남이 구조적으로 불가능해진다.

**잃는 것.** 파일 하나를 열어 전부 훑는 방식이 없어진다. AI 파트가 이슈 댓글에서 지적한 손실이고, 실재한다. 대신 파일명이 시간순 목록을 주고 각 폴더 `README.md`가 훑는 명령을 제시한다 — 문서를 직접 읽으므로 손으로 관리하던 표보다 오히려 정확하다.

**남는 것.** 같은 날 · 추적 키 없음 · 같은 슬러그인 파일을 두 브랜치가 각각 만들면 그때는 다시 겹친다. `worklog/README.md`가 슬러그를 구체적으로 쓰라고 규정하는 것으로 갈음한다. 추적 키가 있어도 날짜와 키가 같은 작업이 겹칠 수는 있다 — `WORKLOG.md`에 같은 날 `Jira 작업`로 묶인 항목이 다섯 개다. 다만 이때도 구분은 슬러그가 지고, 추적 키는 그 위험을 줄일 뿐이다.

**전역 번호는 범위 밖이다.** 원인은 같지만(브랜치마다 같은 자원을 집는다) git이 막지 않는다 — `BD-46-foo.md`와 `BD-46-bar.md`는 파일명이 달라 충돌 없이 둘 다 머지된다. 그래서 이 결정이 잰 비용에 기여하지 않는다. 지금까지 중복 0건이고, 규칙이 이미 `implements/README.md`에 있고, 겹쳐도 고치는 값이 파일 rename 하나로 싸다. 번호를 없애는 대안은 교차 참조 1232곳(96개 파일)을 깨뜨리므로 값이 맞지 않는다 — 번호가 존재하는 이유가 파일명이 바뀌어도 흔들리지 않는 고정 손잡이라는 것이다.

> **후속(2026-08-07).** 위 단락이 예로 든 `BD-46-foo.md`·`BD-46-bar.md`가 실제로 일어났다. 2026-08-03에 `Jira 작업`(목록 정렬)와 `Jira 작업`(datasource 리터럴 제거)가 각자 `BD-46`을 집어 둘 다 머지됐고, 나흘간 중복인 채로 있었다. **"중복 0건"은 이제 1건이다.** 다만 값 판단은 그대로 성립했다 — 고치는 값이 실제로 파일 rename 하나였고, 나중에 머지된 쪽을 [BD-50](BD-50-datasource-redis-config-follows-infra-env-vars.md)으로 옮기며 참조 8곳을 함께 고친 것이 전부다. 이 결정은 유지한다. 재발을 막으려면 번호 채번을 사람의 조회에 맡기지 않는 장치(예: 중복 번호를 잡는 CI 검사)가 필요하고, 그것은 이 결정의 범위 밖이다.

**AI 파트.** `docs/ai/`도 같은 구조라 같은 문제를 갖지만 AI 파트 소유다. 이슈 댓글에서 "각 레포가 자기 문서 구조를 정할 문제이고 `docs/backend/`는 백엔드 판단을 따르겠다", "`docs/ai/`도 분리하신다면 같은 구조로 맞추겠다"고 답했다. 이 결정은 백엔드 구역에만 적용한다.
