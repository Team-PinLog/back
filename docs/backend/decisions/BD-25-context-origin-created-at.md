# BD-25. Context 최초 작성 시각 보존 — `origin_created_at` 도입

- **상태**: Accepted
- **날짜**: 2026-07-27
- **기록**: 당시
- **관련**: [docs#16](https://github.com/Team-PinLog/docs/pull/16) · [BD-07](BD-07-context-immutability.md) 재검토 트리거 발동 · Jira 작업(구현 예정)

## 맥락

[BD-07](BD-07-context-immutability.md)은 Context 불변(수정 = 삭제+생성)을 채택하면서 `created_at`이 새 행 기준으로 갱신되는 것(M2 A안)을 감수 항목으로 남겼고, "최초 작성 시각 보존 요구가 생기면 재검토한다"는 트리거를 걸어 두었다.

프론트에서 그 요구가 실제로 왔다: 수정을 거쳐도 Context의 최초 작성 시각을 유지하고, 목록을 그 시각 기준 **오래된순**으로 기본 정렬해 달라. 트리거 발동이다.

Context 테이블은 아직 마이그레이션·엔티티가 없다(Jira 작업에서 구현 예정). 따라서 이 결정은 스키마 변경이 아니라 공용 계약(데이터모델 §2.5) 선반영으로 처리한다.

## 선택지

| 안 | 장점 | 단점 |
|---|---|---|
| **(a) `origin_created_at` 타임스탬프 컬럼** | 정렬이 `ORDER BY origin_created_at` 단일 컬럼. 값 규칙이 두 줄로 끝남(첫 생성=자신의 `created_at`, 수정=구 값 복사) | 수정 계보(어느 Context에서 왔나)는 추적하지 못함 |
| (b) `origin_context_id` 계보 컬럼 (BD-07 트리거에 언급된 안) | 계보 추적까지 가능 | 정렬하려면 조상 행을 조인·재귀로 타야 함. 계보 추적 요구는 현재 없음 |
| (c) 스키마 무변경, 프론트가 구 `createdAt`을 보관해 정렬 보정 | 백엔드 무변경 | "구 contextId·값을 보관하지 않는다"는 불변 계약(05-1 §1.1)과 정면 충돌. 새로고침하면 소실 |

## 결정

**(a)를 채택한다. 능동적 선택.** 정렬이라는 실제 요구에 필요한 최소가 타임스탬프 하나이고, 계보 추적 요구는 아직 없으므로 (b)는 YAGNI로 제외했다.

값 규칙:

- **첫 생성**: 자신의 `created_at`과 같은 값을 넣는다.
- **수정(교체 생성)**: 구 Context의 `origin_created_at`을 그대로 복사한다. 몇 번을 수정해도 최초 작성 시각이 승계된다.

API 계약: `ContextDetail.createdAt`은 `origin_created_at`을 담는다(프론트 필드 변경 없음). `contexts` 배열 기본 정렬은 `createdAt` 오름차순, 동률이면 `id` 오름차순.

BD-07의 핵심(불변, 수정 = INSERT 먼저 + 소프트 삭제, 새 `contextId` 반환)은 그대로다. BD-07 「결과」의 "정렬·표시" 감수 항목만 이 결정으로 대체된다.

## 결과

**감수하는 것**

- `created_at`(행 생성 시각, 감사용)과 `origin_created_at`(표시·정렬)의 이원화. API로는 "마지막 수정 시각"을 알 수 없다 — 필요해지면 필드 추가로 대응한다.
- 계보 추적은 여전히 불가하다.

**재검토 트리거**

- "수정됨" 표시나 수정 시각 노출 요구가 생기면 → API에 행 `created_at` 노출 필드 추가를 검토한다.
- 수정 계보 추적 요구가 생기면 → `origin_context_id`를 그때 추가한다(이 결정과 공존 가능).
