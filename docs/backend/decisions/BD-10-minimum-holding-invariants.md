# BD-10. 최소 보유 불변식 — 자동 연쇄 삭제 대신 409 확인 후 force

## 맥락

제품 정책에 "빈 그릇을 허용하지 않는다"는 두 규칙이 있다.

```text
활성 Record는 활성 Context를 최소 한 개 가져야 한다.
활성 Collection은 활성 CollectionRecord를 최소 한 개 가져야 한다.
```

이 규칙은 DB 제약으로 표현할 수 없다. 자식 행의 개수를 세는 조건이라 `CHECK`로 걸 수 없고, 부분 유니크로도 표현되지 않는다([BD-09](BD-09-integrity-in-database.md)가 DB에 맡긴 것과 대비된다). 따라서 애플리케이션이 보장해야 한다.

문제는 사용자가 마지막 Context나 마지막 연결을 지우려 할 때다. 그대로 지우면 불변식이 깨지고, 지키려면 부모까지 함께 지워야 하는데 그것은 사용자가 요청하지 않은 파괴다. 게다가 Record 삭제는 그 Record가 마지막인 Collection까지 연쇄될 수 있는데, **프론트는 어느 Collection에서 마지막인지 알 수 없다.** 그 정보는 DB에만 있다.

## 선택지

| 안 | 장점 | 단점 |
|---|---|---|
| (a) 요청대로 지우고 부모를 자동 연쇄 삭제 | 왕복 한 번. 구현 단순 | 사용자가 Context 하나를 지웠는데 Record와 Collection까지 사라진다. 되돌릴 수 없다([BD-07](BD-07-soft-delete-no-restore.md) — 복구 경로가 없다) |
| (b) 마지막이면 그냥 거절 | 안전 | 사용자가 진짜로 전부 지우고 싶을 때 방법이 없다 |
| **(c) 409로 영향 범위를 알려주고, 확인 후 별도 force API** | 파괴 범위를 사용자가 보고 결정한다. 서버만 아는 연쇄 정보를 응답으로 전달 | 왕복 두 번. 엔드포인트가 늘어남(`/force`) |

## 결정

**(c)를 채택한다. — 능동적 선택.**

되돌릴 수 없는 파괴는 **사용자 확인 뒤로 미룬다.** 소프트 삭제를 쓰지만 사용자 복구 기능은 제공하지 않으므로([BD-07](BD-07-soft-delete-no-restore.md)), 연쇄 삭제는 사용자 입장에서 영구적이다.

거절은 `409 DELETE_CONFIRMATION_REQUIRED`이며 `error.impact`에 연쇄 대상(`recordDeleted`, `collectionIds`)을 담는다. 프론트는 이것으로 안내 문구를 만들고, 확인을 받으면 `DELETE /records/{recordId}/force`를 호출한다.

**행 잠금은 자식이 아니라 부모에 건다.** 활성 자식 수를 세고, 그 결과로 분기하고, 쓰기 때문이다. 잠금이 없으면 두 트랜잭션이 각각 "2개니까 지워도 된다"고 판단한 뒤 서로 다른 자식을 지워 활성 수가 0이 될 수 있다. 서로 다른 자식을 지우므로 자식 행 잠금은 겹치지 않으며, **두 작업이 공유하는 유일한 대상이 부모**다.

**이 규칙은 삭제 유스케이스에만 적용된다.** Context 수정은 추가를 먼저 하므로 활성 수가 0이 되는 중간 상태가 없고, 따라서 이 가드에 걸리지 않는다. 수정이 삭제 API를 재사용하지 않는 이유다([BD-06](BD-06-context-immutability.md)).

## 결과

**감수하는 것**

- **왕복 두 번** — 마지막 항목 삭제는 항상 409를 한 번 받는다. 연쇄 대상이 없는 경우에도 `force`는 정상 동작하므로 프론트가 분기를 단순화할 수 있다.
- **엔드포인트 증가** — `DELETE /records/{recordId}`와 `/force` 두 개를 유지해야 한다. 의미가 다른 두 동작이라 통합하지 않는다.
- **역조회 인덱스 필수** — "이 Record가 마지막인 Collection"을 찾아야 하므로 `collection_record(record_id)` 단독 인덱스가 없으면 전체 스캔이 된다. 성능 최적화가 아니라 **기능 요건**이다.
- **잠금 경합** — Context가 많은 Record에서 동시 삭제가 몰리면 부모 행 잠금에서 직렬화된다. 개인 데이터라 동시성이 낮아 수용 가능하다고 봤다.
- **409의 의미 확장** — `error.impact`는 표준 에러 형식에 추가 필드를 붙이는 예외다([08_API_명세 §1.5](https://github.com/Team-PinLog/docs/blob/main/static/08_API_명세.md)).

**재검토 트리거**

- 개인 데이터가 아닌 공유 자원에 같은 패턴이 필요해지면 → 부모 행 잠금의 경합을 다시 측정한다.
- 확인 왕복이 사용자 이탈로 이어진다는 근거가 나오면 → 클라이언트 측 사전 조회로 409를 미리 회피하는 방안을 검토한다. 서버 가드 자체는 유지한다.
