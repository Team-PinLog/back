# BD-09. 무결성을 앱이 아닌 DB에 — `CHECK`·부분 유니크·서로게이트 키

- **상태**: Accepted
- **날짜**: 2026-07-22 (데이터 모델 확립 시점. 단일 커밋으로 특정 불가)
- **기록**: 소급 (2026-07-27 작성)
- **관련**: S15P11A705-76 · `V2__member.sql`
- **공용 계약**: [06_데이터모델_및_무결성 §1.2·§1.4·§3·§4](https://github.com/Team-PinLog/docs/blob/main/static/06_데이터모델_및_무결성.md)

## 맥락

무결성 규칙을 어디서 보장할지 정해야 했다. 중복 가입 금지, 동일 장소 중복 저장 금지, 자기 팔로우 금지, 본문 공백 금지, 좌표 범위 같은 규칙이 있고, 각각을 애플리케이션 검증으로 둘 수도 DB 제약으로 둘 수도 있었다.

애플리케이션 검증만 두면 동시 요청에서 뚫린다. 두 트랜잭션이 각각 "중복 없음"을 확인한 뒤 둘 다 INSERT하면 검증이 무의미해진다.

## 선택지

| 안 | 장점 | 단점 |
|---|---|---|
| (a) 애플리케이션 검증만 | 에러 메시지를 사용자 언어로 바로 만들 수 있음. DB 이식성 | 동시 요청에 뚫린다. 검증을 빠뜨린 경로가 생기면 조용히 깨진 데이터가 쌓인다 |
| (b) 전부 DB 제약으로 | 어떤 경로로 들어와도 막힌다 | 자식 행 개수를 세는 규칙은 `CHECK`로 표현할 수 없다. 억지로 트리거를 쓰면 로직이 DB에 숨는다 |
| **(c) 단일 행으로 판정 가능한 것은 DB, 개수를 세는 것은 애플리케이션** | 표현 가능한 것은 최후 방어선을 DB에 두고, 불가능한 것만 애플리케이션이 잠금으로 처리 | 두 곳을 봐야 전체 규칙을 안다 |

## 결정

**(c)를 채택한다. 능동적 선택.** 판정에 필요한 정보가 **한 행 안에 있으면 DB**, 자식 행을 세어야 하면 애플리케이션이다.

**DB가 보장하는 것**

| 규칙 | 방식 |
|---|---|
| 동일 소셜 계정 중복 가입 금지 | `(provider, provider_user_id)` 활성행 부분 유니크 |
| 동일 Kakao Place 중복 저장 금지 | `UNIQUE(kakao_place_id)` (전체 유니크. Place는 삭제하지 않음) |
| User당 활성 Record는 Place별 최대 1개 | `(member_id, place_id)` 활성행 부분 유니크 |
| Collection 내 동일 Record 중복 금지 | `(collection_id, record_id)` 활성행 부분 유니크 |
| 동일 Shelf 중복 Follow 금지 | `(followee_member_id, follower_member_id)` 활성행 부분 유니크 |
| 자기 Shelf Follow 금지 | `CHECK (followee_member_id <> follower_member_id)` |
| 본문·제목 공백만 금지 | `CHECK (length(btrim(...)) > 0)` |
| 좌표 범위 | `CHECK (lat BETWEEN -90 AND 90)` 등 |

유니크가 **모두 활성행 부분 유니크**인 것은 [BD-07](BD-07-soft-delete-no-restore.md)의 직접 귀결이다. 전체 유니크로 두면 삭제 후 재저장이 실패한다.

**애플리케이션이 보장하는 것** — 활성 Context 최소 1개, 활성 CollectionRecord 최소 1개. 자식 개수를 세는 조건이라 제약으로 표현되지 않는다. 부모 행 잠금으로 처리한다([BD-10](BD-10-minimum-holding-invariants.md)).

**함께 확정한 두 가지**

- **서로게이트 키를 쓴다.** 기본키는 `BIGINT GENERATED ALWAYS AS IDENTITY`이며 외부 시스템 식별자(`kakao_place_id`)를 기본키로 쓰지 않는다. 외부 id는 우리가 통제하지 못하고, 카카오 병합·재등록으로 바뀔 수 있다([BD-18](BD-18-place-snapshot.md)). 바뀌면 모든 FK가 함께 흔들린다.
- **`user` 대신 `member`를 쓴다.** `user`는 PostgreSQL 예약어다. 도메인 용어는 User로 유지하되 물리 테이블만 `member`로 둔다.

## 결과

**감수하는 것**

- **에러 번역이 필요하다.** 제약 위반이 DB 예외로 올라오므로 사용자 언어의 메시지로 옮기는 계층이 필요하다. 어떤 제약이 깨졌는지 예외에서 식별해야 한다.
- **규칙이 두 곳에 나뉜다.** 전체 무결성을 알려면 마이그레이션과 서비스 코드를 함께 봐야 한다. [06 §4](https://github.com/Team-PinLog/docs/blob/main/static/06_데이터모델_및_무결성.md)의 두 표가 그 목차 역할을 한다.
- **제약 변경이 마이그레이션이다.** 규칙을 고치려면 새 `V2~V99` 마이그레이션이 필요하고, 이미 적용된 마이그레이션은 수정할 수 없다.
- **PostgreSQL 종속이 깊어진다.** 부분 유니크 인덱스는 PostgreSQL 기능이다. 이미 [BD-01](BD-01-h2-removal-testcontainers.md)에서 PostgreSQL 전용을 택했으므로 새로 생기는 비용은 아니다.
- **도메인 용어와 테이블명이 어긋난다.** 코드에서 User와 `member`를 오간다.

**재검토 트리거**

- 자식 개수 규칙이 늘어나 애플리케이션 잠금이 여러 곳으로 퍼지면 → 공통 가드로 추출할지 검토한다.
- 다른 DBMS 이식 요구가 생기면 → 부분 유니크를 대체할 방법이 없으므로 이 결정부터 다시 본다. 현재는 상정하지 않는다.
