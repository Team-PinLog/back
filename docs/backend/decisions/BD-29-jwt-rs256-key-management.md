# BD-29. 세션 JWT를 RS256으로 서명하고, 키는 환경변수 주입 + 운영 fail-fast

- **상태**: Accepted
- **날짜**: 2026-07-28
- **관련**: S15P11A705-63
- **관련 결정**: [BD-21](BD-21-auth-token-model.md)(토큰 모델의 원본) · [BD-28](BD-28-authorization-request-in-cookie.md)

## 맥락

[BD-21](BD-21-auth-token-model.md)이 토큰 모델(JWT, Access 30분 / Refresh 7일, `HttpOnly` 쿠키)까지 정했지만 **서명 알고리즘과 키 관리는 정하지 않았다.** 발급을 구현하려면 이 둘이 먼저 필요하다.

먼저 확인한 것은 **외부 규범이 이 선택을 정해 주는지**였다. 결론은 "정해 주지 않는다"이고, 근처 문서가 하는 말의 적용 범위가 우리와 다르다.

- [RFC 9068](https://www.rfc-editor.org/rfc/rfc9068.html) §4는 JWT access token에 대해 *"use of asymmetric cryptography is RECOMMENDED **as it simplifies the process of acquiring validation information for resource servers**"* 라고 하고 `RS256` 지원을 MUST로 건다. 그러나 **권고 이유가 발급자(AS)와 검증자(RS)의 분리를 전제한다.** 우리는 BFF와 리소스 서버가 한 프로세스라(S15P11A705-63 티켓) 이 이유가 성립하지 않는다. 애초에 이 프로파일이 규정하는 "OAuth access token"도 우리 세션 쿠키와 다른 물건이다.
- [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html)(BCP 225)는 대칭/비대칭에 **중립**이다. 알고리즘 *선택*이 아니라 *다루는 방법*을 규정한다.
- `draft-ietf-oauth-browser-based-apps`(현재 -27, 아직 RFC 아님)는 BFF + 쿠키 세션을 우리와 같은 구조로 다루지만 세션 토큰의 서명 알고리즘은 규정하지 않는다. BD-21이 인용한 것도 이 문서의 *토큰 보관 위치* 권고지 서명 얘기가 아니었다.

즉 **"IETF가 RS256을 요구해서"가 아니다.** 그렇게 적으면 사실이 아니다.

## 선택지

| 안 | 장점 | 단점 |
|---|---|---|
| (a) HS256 대칭키 | 키가 문자열 하나. 주입·로컬 개발이 가장 단순하다. 지금 구조(발급자=검증자)에 부족한 점이 없다 | 검증 주체가 프로세스 밖으로 나가는 순간 비밀 공유가 강제된다. 그때 알고리즘을 바꾸면 이미 발급된 토큰과 키 배포 방식을 함께 갈아야 한다 |
| (b) RS256 비대칭키 | 검증자가 분리돼도 공개키만 넘기면 된다. RFC 9068이 지원을 MUST로 거는 알고리즘이라 나중에 OAuth 프로파일에 맞출 때 추가 작업이 없다 | 키 배포·보관 설계를 **지금** 떠안는다. PEM은 `unset` 같은 더미 문자열로 대체할 수 없어 로컬·CI 경로를 따로 만들어야 한다 |
| (c) ES256 | 서명·검증이 RS256보다 빠르고 키가 짧다 | 지금 성능이 문제가 아니고, RFC 9068이 MUST로 거는 것은 RS256이라 상호운용에서 한 겹 덜 안전하다 |

## 결정

**(b) RS256.** — **능동적 선택.**

결정적 이유는 성능도 규범 준수도 아니라 **되돌리는 비용의 비대칭**이다. 지금 HS256으로 두면 나중에 검증자를 분리할 때 알고리즘·키 배포·발급된 토큰 호환을 한꺼번에 바꿔야 한다. RS256으로 시작하면 그때 필요한 것은 공개키를 넘기는 일(또는 JWKS 엔드포인트 추가)뿐이다. **지금 필요해서가 아니라 나중 마이그레이션을 피하려고 선불로 내는 값이며, 그 대가가 아래 "감수하는 것"이다.**

함께 정한 것:

| 항목 | 값 | 이유 |
|---|---|---|
| 알고리즘 | `RS256` (RSA 2048 이상) | RFC 7518이 RS256에 2048비트 이상을 요구한다 |
| 키 주입 | 환경변수로 PEM. 운영은 Kubernetes Secret | `DB_PASSWORD`·`GOOGLE_CLIENT_SECRET`과 같은 경로다([설정 규약](../../development/configuration.md)). 새 메커니즘을 만들지 않는다 |
| 키 미주입 시 | 로컬·테스트는 **기동 시 임시 키쌍 생성**, 운영 프로파일은 **기동 실패(fail-fast)** | 아래 참조 |
| `kid` 헤더 | **넣는다** (회전 구현은 이번 범위 아님) | 없으면 나중에 키를 바꿀 때 전면 로그아웃이 강제된다. 지금 넣는 비용이 거의 0이다 |
| JWKS 엔드포인트 | **두지 않는다** | 검증자가 자기 자신이라 쓸 곳이 없다. 공개 경로와 관리 대상만 는다. 분리 시점에 추가한다 |
| 검증 시 알고리즘 | 허용 목록으로 **고정**. 토큰 헤더의 `alg`를 신뢰하지 않는다 | RFC 8725 §3.1 — *"Libraries MUST enable the caller to specify a supported set of algorithms and MUST NOT use any other algorithms"*. alg confusion 방어선이다 |
| 라이브러리 | nimbus-jose-jwt | **기본값 수용** — `spring-boot-starter-security-oauth2-client`가 이미 끌고 와서 의존성이 늘지 않는다. jjwt를 물린 이유는 "API가 조금 간결하다"가 트레이드오프의 전부여서다. 별도 BD를 만들 무게가 아니라 여기 한 줄로 남긴다 |

**키 미주입 시 동작을 프로파일로 가른 이유.** 기존 설정은 `${GOOGLE_CLIENT_ID:unset}`처럼 더미 기본값으로 "실제 키 없이도 CI가 뜨게" 해 왔다. RSA PEM에는 이 수법을 쓸 수 없다 — 파싱 가능한 키여야 한다. 그렇다고 임시 생성 경로를 운영에서도 열어 두면 **파드마다 다른 키가 생겨 스케일아웃·재시작 때 전면 로그아웃**이 된다. 조용히 망가지는 쪽보다 뜨지 않는 쪽이 낫다. 임시 생성은 인증 *우회*가 아니라 키 *공급*이므로 [인증 계약](../../development/authentication.md) §4의 "로컬에서 인증을 통째로 우회하는 설정은 두지 않는다"에 걸리지 않는다.

## 결과

**감수하는 것**

- **키 배포·보관 설계를 지금 떠안는다.** HS256이면 문자열 하나로 끝날 일이 PEM 주입·프로파일별 분기·임시 키 생성 경로가 된다. (b)를 고른 대가 그 자체다.
- **운영에서 키가 없으면 기동하지 않는다.** 의도한 동작이지만, 배포 시 Secret 누락이 곧 파드 기동 실패다. Infra 쪽에 이 값이 필수라는 사실이 전달되어야 한다.
- **회전은 아직 없다.** `kid`만 심어 두고 다중 키 검증은 구현하지 않는다. 지금 키를 바꾸면 여전히 전면 로그아웃이다.
- **RSA 서명 비용.** ES256보다 느리고 토큰도 길다. 지금 트래픽에서 문제될 수준이 아니라고 판단했을 뿐, 측정한 값은 없다.
- **이 결정의 값이 실현되지 않을 수 있다.** 서비스를 끝까지 한 프로세스로 운영하면 (a)로 충분했다는 뜻이 된다. 보험료를 낸 것이고, 보험이 안 쓰일 수 있다.

**재검토 트리거**

- **토큰 검증 주체가 발급 프로세스 밖으로 나가면** → JWKS 엔드포인트를 추가한다. 알고리즘 변경은 불필요하다 — 이 트리거를 싸게 넘기려고 지금 RS256을 고른 것이다.
- **키 회전이 실제 요건이 되면** → `kid` 기반 다중 키 검증(신·구 키 동시 수용)을 구현한다.
- **서명 비용이 측정 가능한 문제가 되면** → ES256으로 옮긴다. 비대칭 안에서의 이동이라 키 배포 구조는 유지된다.
- **BD-21의 만료 수치 재검토가 발동하면** 이 문서도 함께 본다. 키 수명과 토큰 수명은 같이 정해야 한다.
