# BD-34. Feed 페이지네이션을 Redis Session Cache 대신 `requestId` seed 기반 결정적 재계산으로 만든다

- **상태**: Accepted
- **날짜**: 2026-07-29
- **관련**: Jira 작업, [back#58](https://github.com/Team-PinLog/back/issues/58),
  [P42](../../ai/proposals/P42-feed-mvp-without-place-metadata.md),
  AI 파트 명세 [feed-profile-cache](../../ai/spec/feed-profile-cache.md) 7장 ·
  [feed-recommendation](../../ai/spec/feed-recommendation.md) 4장

## 맥락

Feed 목록은 opaque cursor로 페이지를 잇는다. 문제는 **후보 풀을 어떻게 페이지 사이에 보존하는가**다.
매 페이지마다 후보를 새로 뽑으면 그 사이 점수가 흔들려 항목이 중복되거나 누락된다.

AI 파트 명세는 이 자리에 Redis Session Cache(`feed:session:{requestId}`, TTL 10분)를 둔다.
그런데 같은 명세가 함께 요구하는 것이 두 가지 더 있다.

- Redis 장애 시 Cache 미사용으로 폴백해 **정상 응답**해야 한다(feed-recommendation 5장).
- Session이 만료됐거나 없으면 새 Session으로 첫 페이지부터 시작한다. 오류가 아니다(K9).

즉 Session Cache가 있어도 **없을 때 동작하는 경로가 반드시 따로 있어야 한다.** 그리고 이 티켓의
필수 범위(1~5)에 Redis Profile Cache는 들어 있지 않다. Redis 의존을 새로 들이면 Feed 조회 경로가
장애 전파 면에서 인증 경로와 같은 등급이 된다.

무작위 채널만 비결정적이고 나머지(점수·다양성 조정·배치)는 이미 순수 함수라는 점도 확인했다.

## 선택지

| 안 | 장점 | 단점 |
|---|---|---|
| **(a) `requestId`를 무작위 채널의 seed로 삼아 페이지마다 결정적으로 재계산** | Redis 의존이 없어 장애 폴백 경로가 곧 정상 경로다. 상태가 커서 하나뿐이라 만료·역직렬화 실패 같은 실패 모드가 없다 | 페이지마다 후보 쿼리 3회 + 특징·노출 집계가 반복된다 |
| (b) 명세대로 Redis Session Cache + (a)를 폴백으로 함께 구현 | 명세와 완전히 일치하고 2페이지 이후가 싸다 | 같은 정렬을 만드는 경로가 둘이 되고, 둘이 어긋나면 페이지 경계에서만 재현되는 버그가 된다. 이번 범위에서 Redis 계층 전체(직렬화·타임아웃·차단)가 함께 들어와야 한다 |
| (c) 커서에 마지막 항목의 점수·id를 실어 keyset 방식으로 이어가기 | 상태가 없고 페이지 비용이 싸다 | 점수는 요청 시점 계산값이라 정렬키로 안정적이지 않다. 탐색 슬롯 배치가 점수 순서와 무관해 keyset으로 표현되지 않는다 |

## 결정

**(a)를 골랐다. 능동적 선택이다.**

결정적 이유 둘.

1. **명세가 이미 "Cache 없이도 도는 경로"를 요구한다.** (b)를 고르면 그 경로를 어차피 만들어야
   하고, 그러면 정렬을 만드는 코드가 둘이 된다. 하나로 두고 나중에 Cache를 **그 앞에 얹는** 편이
   순서가 맞다.
2. **지켜야 할 것은 계약이지 기법이 아니다.** 명세가 Session Cache로 달성하려는 것은 "페이지 간
   중복·누락 없음"(K10·Q4)이고, seed 고정 + 결정적 정렬이 같은 성질을 만든다. 가중치·채널 배분·
   탐색 슬롯 같은 **정책 수치는 하나도 건드리지 않았다.**

구현에서 결정성을 만드는 지점은 셋이다.

- 무작위 채널은 `requestId`에서 유도한 seed로 id 범위 표본의 시작점을 정한다(`ORDER BY random()`
  전체 스캔을 쓰지 않는다는 명세 요구와도 같은 방향이다).
- 점수 동점은 `publishedAt DESC`, `collectionId DESC`로 끝까지 가른다. 동점 구간의 순서가
  정렬 알고리즘에 좌우되면 페이지 경계에서 항목이 새거나 겹친다.
- 다양성 조정과 탐색 슬롯 배치에 난수를 쓰지 않는다. 탐색 항목은 하위 절반에 **계산된 간격으로**
  분산한다.

커서는 Feed 전용 형식을 만들지 않고 공통 `Cursor`(`Base64(정렬키,id)`)의 정렬키 자리에
`requestId`, id 자리에 offset을 넣어 재사용한다.

## 결과

- **이 결정으로 감수하는 것**
  - 페이지마다 후보 쿼리 3회 + 특징 집계 1회 + 노출 집계 1회가 반복된다. 후보 200건 기준이라
    비용이 후보 수에 비례하지 페이지 수에 비례하지는 않지만, Session Cache가 있을 때보다 2페이지
    이후가 비싸다.
  - **DB가 그 사이 바뀌면 정렬이 바뀔 수 있다.** 새 Collection이 발행되면 다음 페이지에서 한 항목이
    밀려 중복 노출될 수 있다. Session Cache는 id 목록을 얼려 이걸 막지만, 그 대신 삭제·비공개
    전환이 stale해진다 — 그쪽은 어차피 최종 재검증이 막는다. 어느 쪽도 완전하지 않고, 우리는
    "얼리지 않는 대신 최신 상태를 본다"를 골랐다.
  - IMPRESSION이 `position`을 페이지 내 0-based로 기록하므로, 페이지가 밀리면 같은 Collection이
    다른 position으로 두 번 기록될 수 있다. 패널티는 `COUNT(DISTINCT request_id)`라 영향받지 않는다.
- **재검토 트리거**
  - 후보 풀을 200보다 크게 올리거나, 페이지 지연이 문제로 관측될 때. 그때 Session Cache를 이
    경로 **앞에** 얹는다(폴백은 지금 코드 그대로 남는다).
  - Redis Profile Cache(이 티켓의 후속 범위)를 실제로 도입할 때. Redis가 이미 Feed 경로에 들어와
    있다면 (b)의 비용 계산이 달라진다.
