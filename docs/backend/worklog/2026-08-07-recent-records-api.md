# 최근 7일 내 작성한 내 Record 목록 API를 더했다

- **날짜**: 2026-08-07
- **추적**: Jira 작업
- **관련**: [명세 5.9](https://github.com/Team-PinLog/docs/pull/50) · [BD-13](../decisions/BD-13-public-boundary-query-dto-split.md) · [BD-18](../decisions/BD-18-keyword-preset-and-visibility.md)

홈 화면 "최근 기록" 영역이 쓸 `GET /v1/records/recent`를 더했다. 마이그레이션은 없다.

## 경로를 `/recent`로 둔 것

`GET /v1/records` 루트를 나중의 "내 전체 Record 목록" 자리로 비워 뒀다. 지금 요구는 7일 창이 붙은
특수 조회인데 이것을 루트에 박으면, 전체 목록이 필요해질 때 같은 경로의 의미가 바뀌거나 창을 끄는
파라미터를 덧붙이게 된다.

기간·정렬 파라미터를 두지 않았다. Collection 계열은 `sort`를 받지만(BD-46) 그쪽은 방향이 화면마다
갈린다. 여기는 "최근"이 곧 정렬이라 오래된순으로 뒤집을 수 있는 `/recent`는 이름과 동작이 어긋난다.

## `RecordDetailResponse`를 재사용하지 않은 것

카드에 Context 본문을 싣지 않기로 했는데, `RecordDetailResponse`를 그대로 쓰면 이 응답에서는 항상
비워 보내야 하는 자리가 생긴다. 비워 보내는 자리는 언젠가 누가 채운다. `RecentRecordCardResponse`를
따로 만들어 자리 자체를 없앴다 — 실수가 유출이 아니라 컴파일 오류로 끝난다. `PublicRecordCardResponse`가
`contexts`를 고정 `null`로 둔 것(BD-13)과 같은 이유이며 한 걸음 더 간 것이다.

`keywordStatus`는 싣지 않았다. 이 목록은 갓 만든 Record만 보여주므로 AI 판정 전인 항목이 검색보다
오히려 흔하고, 그래서 화면이 "분석 중"과 "키워드 0건"을 구분하지 못하는 back#136의 문제를 그대로
안는다. 지금은 싣지 않기로 정했고, 필요해지면 `findKeywordStatusForOwner`가 이미 있으므로 쿼리
하나와 필드 하나를 더하는 하위 호환 변경으로 닫는다. PR 본문에서 프론트에 이 점을 명시했다.

## 인덱스를 더하지 않은 것

`ix_record_member (member_id, deleted_at)`로 회원 단위로 좁힌 뒤 정렬한다. 회원당 활성 Record가
수십~수백 규모라 정렬 비용이 문제가 되지 않는다 — 지도 마커 쿼리가 keyword LIKE에 인덱스를 붙이지
않은 것과 같은 근거다. 규모가 달라지면 그때 `(member_id, created_at DESC, id DESC)`를 더한다.
마이그레이션이 없다는 것이 이 변경의 장점이라, 지금 쓰지 않을 인덱스로 그것을 버리지 않았다.

## 커서와 7일 창이 겹치는 지점

`since`는 요청마다 다시 계산되므로 페이징 도중 창의 뒤쪽 경계가 앞으로 밀린다. 커서를 오래 쥐고
있다가 다음 페이지를 부르면 경계에 걸린 항목이 빠질 수 있다. 정렬이 최신순이고 커서가
`(createdAt, id)`보다 작은 것만 읽으므로 **이미 준 항목이 다시 나오지는 않는다.**

커서에 `since`를 실어 창을 고정하는 안을 검토했으나 하지 않았다. 커서 형식(`정렬키,id`)을 바꿔야
하고, 밀려나는 항목은 정확히 "7일이 지나서 이제 이 목록의 대상이 아닌 것"이라 사라지는 편이 계약에
맞다.

## 테스트에서 걸린 것

**엔드포인트가 없을 때 404가 아니라 400이 났다.** `/v1/records/recent`가 `GET /v1/records/{recordId}`에
걸려 `"recent"`를 `Long`으로 바꾸려다 실패한 것이고, 그 오류 코드가 위조 커서 거절과 같은
`INVALID_INPUT`이었다. 그래서 위조 커서 테스트가 **매핑이 없어도 통과했다.** 진짜 커서로 200을 먼저
받아 내는 단계를 앞에 두어 매핑 부재가 반드시 드러나게 고쳤다.

쿼리 카운트 테스트는 구현 뒤에 썼으므로 처음부터 통과했다 — 그것만으로는 아무것도 증명하지 못해서,
Place 조회를 일부러 Record별 반복으로 되돌려 실패하는 것을 보고 되돌렸다. 기본 페이지 크기가 1이라
N+1로 짜도 기본 요청에서는 증상이 없고 프론트가 `size`를 올릴 때만 드러난다. 그래서 이 측정을 남긴다.
