# 탈퇴를 인가 왕복 뒤로 옮겨 공급자 연결을 먼저 끊게 했다

- **날짜**: 2026-08-04
- **추적**: Jira 작업
- **관련**: [BD-48](../decisions/BD-48-unlink-before-withdrawal.md) · [BI-38](../implements/BI-38-2026-08-04-unlink-before-withdrawal.md) · [back#176](https://github.com/Team-PinLog/back/issues/176) · docs `c5b09d9`(08 §3.6 개정)

`DELETE /v1/me`가 즉시 지우던 것을 왕복 시작으로 바꿨다. 공급자 인가를 다시 받아 그 access token으로 연결을 끊고, **끊긴 뒤에만** 소프트 삭제한다.

## 왜 순서를 뒤집었나

06 §6.9가 소프트 삭제와 함께 `provider_user_id` 마스킹을 요구한다. 지우고 나면 공급자에서 그 사용자를 지목할 수단이 사라지므로, 해제 실패를 **나중에 재시도할 수도 없다**. 큐에 넣어 두는 설계가 성립하지 않는 이유가 이것이다 — 큐에 넣을 식별자가 이미 파기됐다.

그래서 Jira 작업의 "공급자 장애가 탈퇴를 막아서는 안 된다"를 명시적으로 뒤집었다. 장애로 인한 지연은 일시적이고 재시도로 풀리지만, 반대 순서의 대가(영구 미이행 + 동의 없는 재가입)는 회복 경로가 없다.

## 이번에 바뀐 판단

작업 중에 초안을 세 번 고쳤다.

**토큰을 보관하지 않기로 한 것**은 최소권한 때문이지 공급자 제약 때문이 아니다. [back#139](https://github.com/Team-PinLog/back/issues/139)가 찾아둔 refresh token 저장안은 기술적으로 가능하다. 리뷰에서 이 전제가 지적됐고 맞는 지적이라 [176 코멘트](https://github.com/Team-PinLog/back/issues/176#issuecomment-5173384371)로 정정했다. 조사하면서 Google이 `access_type=offline`을 요구하고 **첫 인가에만** refresh token을 준다는 것도 확인해 BD-48을 고쳤다.

**재시도를 뺐다가 다시 넣었다.** "별도 PR" 로 미루려 했는데, 214를 뒤집는 근거가 "실제 거절은 드물어진다"였다. 흡수 장치가 없으면 그 근거가 빈다. 같은 단위로 넣는 게 맞았다.

**Naver 엔드포인트를 근거 있는 상태에서 흔들었다 — 가장 나쁜 실수였다.** 구현은 공급자 공식 문서(§4.3 Token Revocation)를 근거로 `POST /oauth2.0/revoke` + 상태 코드 판정으로 했다. PR 리뷰에서 *"연동 해제는 `grant_type=delete`이고 실패도 200 본문으로 온다"*는 지적을 받자, **이미 손에 있던 그 문서를 다시 읽지 않고** 웹 검색 결과를 따라 방향을 틀었다. javadoc에 "엔드포인트 미확정"을 적고, 문서가 명시적으로 없다고 한 응답 형태(200 + `error`)를 방어하는 코드와 테스트까지 넣었다.

전부 되돌렸다. 네이버가 연동 해제를 OAuth 2.0 표준 용어로 개정하면서 엔드포인트가 바뀐 것이고, **검색에 걸린 자료들이 낡은 쪽**이었다. 원래 구현이 맞았다.

남길 교훈은 "리뷰를 무시하라"가 아니다. 지적 덕분에 1차 출처를 확인해 근거가 단단해졌다. 틀린 것은 **순서**다 — 반박을 받으면 이미 가진 1차 출처를 먼저 다시 읽고, 없을 때만 검색한다. 검색 결과가 공식 문서와 어긋나면 자료의 최신성을 먼저 의심한다.

**`?withdrawal=completed`를 만들었다가 걷어냈다.** 명세를 확인하지 않고 정한 값인데, 08 §3.6.2가 성공에 표시를 두지 않기로 이미 결정해 뒀다. 근거도 명확하다 — 쿠키가 만료된 채 착지하므로 클라이언트의 기존 앱 시작 흐름이 알아서 로그인으로 보낸다. 프론트의 콜백 검증 스키마가 `error` 외의 쿼리를 버려서 **도달하지도 않았다.**

## 되돌릴 수 없는 경로를 찾아 닫았다

구현이 끝난 뒤 시나리오를 다시 훑다가 두 개를 찾았다.

- **소셜 계정이 둘이면** 한 왕복으로 하나만 끊는데 마스킹은 전부에 걸린다 — 이 설계가 막으려던 상태를 이 설계가 만든다. 시작·완료 양쪽에서 거절한다. 지금은 계정 생성 경로가 로그인 하나뿐이라 도달할 수 없지만, 계정 연결 기능이 붙는 순간 조용히 깨진다.
- **이미 탈퇴한 회원의 두 번째 왕복**이 "남의 계정"과 같은 코드로 나갔다. 완료로 다룬다. 그 왕복이 만든 새 인가는 끊지 않는다 — 마스킹으로 소유를 확인할 수 없고, 확인 없이 끊으면 BD-48 §⑤가 막으려는 경로가 열린다.

그리고 **테스트가 잡지 못하던 전제 둘**을 고정했다. 공급자 토큰이 성공 핸들러에 닿는 순서(핸들러를 단위로 부르며 토큰을 손으로 넣으면 검증되지 않는다)와, `attributes`를 더할 때 PKCE `code_verifier`가 살아남는 것(잃으면 인가는 성공하고 토큰 교환만 죽는다). 둘 다 틀리면 탈퇴가 통째로 불가능한데 증상은 콜백 실패 하나로만 보인다.

## 프론트가 아직 이 계약을 모른다

프론트의 탈퇴는 `[Jira 작업]`(front#37) 시점 그대로다. `deleteAccount()`가 응답 본문을 버리고(`Promise<void>`), `authorizationUrl`이 레포 전체에 없고, 콜백은 `error`만 읽는다.

**배포 순서가 어긋나면 "탈퇴가 완료되었습니다"가 뜬 채 아무것도 지워지지 않는다.** `logged_in`이 살아 있어 `/login` 가드가 홈으로 되돌리기까지 한다. 백엔드와 프론트가 함께 나가야 한다.
