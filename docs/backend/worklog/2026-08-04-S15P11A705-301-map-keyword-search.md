# 지도 마커 API에 keyword 검색과 이름순 정렬을 더한다

- **날짜**: 2026-08-04
- **추적**: S15P11A705-301
- **관련**: [docs#45](https://github.com/Team-PinLog/docs/pull/45) (08 §4.2·§13.11 계약 선행 개정)

컬렉션에 담을 장소 선택 화면이 `GET /v1/records/map`을 목록으로 재사용하는데, 장소가 수백 개로 늘면 거를 수단이 없었다. 별도 목록 API를 파는 대신 기존 API에 선택 파라미터 `keyword`(장소명·주소 부분 일치, 대소문자 무시)를 더했다 — 이 쿼리는 `record.member_id`로 드라이빙하고 place는 PK 조인이라, 검색 조건은 회원 단위로 좁혀진 행에 필터로만 붙는다. 인덱스·마이그레이션이 필요 없는 이유다.

구현 중 내린 판단 둘:

1. **LIKE 패턴 가공(소문자화·이스케이프·`%` 감싸기)을 쿼리의 `concat`이 아니라 서비스에 뒀다.** `lower(concat('%', :keyword, '%'))` 안의 null 파라미터는 Postgres가 타입을 추론하지 못해 `lower(bytea)` 오류가 된다(테스트에서 재현). `like`의 우변 자리는 text로 고정되어 안전하다. 이스케이프 문자는 백슬래시 대신 `!` — JPQL 문자열 리터럴 규칙과 겹치지 않게.
2. **이름순 정렬을 DB `ORDER BY`가 아니라 서비스의 Java `Collator`(한국어 로케일)로 했다.** 테스트 컨테이너에서 `ORDER BY p.name`이 입력 순서를 그대로 내놓았다 — 한글에 동순위 가중치를 주는 collation에서는 이름 정렬이 사실상 무순서고, 같은 코드가 운영 DB와 테스트 DB에서 다른 순서를 내놓는 환경 의존이 생긴다. 응답이 회원 단위(수십~수백 행)라 애플리케이션 정렬 비용은 무시할 수준이다.

빈 keyword(생략·빈 문자열·공백)는 400이 아니라 "필터 없음"이다 — 검색창을 지운 것이 오류일 수는 없다. bbox 4개 규칙("모두 주거나 모두 생략")에 keyword는 포함되지 않는다.
