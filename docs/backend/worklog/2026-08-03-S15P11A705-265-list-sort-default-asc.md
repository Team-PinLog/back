# 목록 정렬 기본을 오래된순으로 뒤집고 방향 파라미터를 연다

- **날짜**: 2026-08-03
- **추적**: S15P11A705-265
- **관련**: [BD-46](../decisions/BD-46-list-sort-default-asc-with-params.md) · [docs#42](https://github.com/Team-PinLog/docs/pull/42) · [docs#37](https://github.com/Team-PinLog/docs/pull/37) (계승됨)

Collection 목록·Collection 내부 Record·Record 상세 contexts의 기본 정렬을 최신순에서
오래된순으로 뒤집고, 방향을 여는 파라미터를 더했다 — `sort`(7.2·9.3·8.1),
`collectionSort`(9.2 동봉 페이지), `recordSort`(7.3), `contextSort`(5.2). 파라미터는 사용자
토글이 아니라 프론트가 상수로 고정해 보내는 값이다. 왜 이 모양인지는 BD-46.

판단들:

- **방향별로 쿼리 메서드를 나눴다.** `order by`와 커서 비교 부등호(`<`/`>`)가 함께 뒤집혀야
  하는데, 방향을 파라미터로 섞으면 한쪽만 뒤집힌 실수가 컴파일과 단순 조회 테스트를 통과한다.
  `...Desc`/`...Asc` 짝으로 나누면 잘못 고른 것이 이름에 드러난다.
- **창 함수 쿼리는 SQL 상수 둘로 갈랐다.** `ORDER BY`는 바인드 파라미터를 받지 못한다.
  조립 재료가 사용자 입력이 아니라 `"ASC"`/`"DESC"` 리터럴뿐임을 코드 모양으로 보였다.
- **9.2 동봉 페이지와 8.1을 티켓 명시 없이 포함했다.** 9.2 동봉 페이지의 커서를 9.3이
  이어받는 한 계약이라 방향이 갈라지면 커서가 끊기고, 8.1은 9.3과 같은 발행 Collection
  조회를 공유해 기본값 변경이 어차피 전파된다 — 파라미터 없이 방향만 바뀌면 그쪽이 더 어색하다.
- **정렬 테스트는 양방향을 모두 걷는 파라미터화로 짰다.** 첫 페이지 순서만 보면 커서 쿼리의
  부등호 짝이 틀린 것을 못 잡는다 — size=1로 끝까지 걸어 중복·누락 없음을 단언한다.
- **파라미터화 픽스처의 place 키에 실행 값을 섞었다.** `kakaoPlaceId`가 전역 유니크라 두 번째
  실행이 같은 키로 유니크 위반을 냈다(RED 단계에서 발견).
- **정의되지 않은 정렬값의 400은 프레임워크 매핑에 맡겼다.** enum 바인딩 실패가
  `GlobalExceptionHandler`의 4xx → `INVALID_INPUT` 경로로 떨어진다. 테스트로만 고정했다.
- **인덱스 마이그레이션 없음.** btree 역방향 스캔이 ASC 조회를 받는다(데이터모델 3.3에 명시).
- **커서-방향 불일치 검증은 보류.** 상수 전제 위의 선택이며, 정렬 토글 UI가 생기면 커서에
  방향을 싣는 작업이 선행돼야 한다 — 재검토 트리거와 권고 구조는 BD-46에 있다.
