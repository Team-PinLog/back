# P46: Feed 응답 Keyword의 표시 정렬 기준 — 축 라운드로빈 상위 4개

- **상태**: Accepted
- **날짜**: 2026-08-03
- **관련**: S15P11A705-278,
  [ai#93](https://github.com/Team-PinLog/ai/issues/93)(제기 — 프론트),
  [front#88](https://github.com/Team-PinLog/front/issues/88)(S15P11A705-279 책장 레이아웃),
  S15P11A705-252([back#146](https://github.com/Team-PinLog/back/pull/146) — 표시값 경계)
- **주도(Driver)**: AI 파트

## 맥락

`GET /api/core/v1/feed/collections` 응답의 `keywords`에는 **개수 상한이 없었다.** 프론트가 Feed를
책장 레이아웃으로 바꾸면서 카드에 실을 Keyword 수를 고정해야 했고, "상위 4개"를 요청했다.

그런데 **「상위」의 근거가 코드에도 명세에도 없었다.** 08 §10.1과 `feed-recommendation.md` 3.7
어디에도 개수·정렬 규칙이 없다. 개수를 자르는 일이 아니라 **정렬 기준을 정하는 일**이다.

**한 가지 전제는 사실과 달랐다.** 티켓은 현재 순서를 "SQL `GROUP BY` 결과 순서"로 적었으나,
`FeedService.RankedFeed.keywordsOf`는 `S15P11A705-120`(back#77) 때부터 `.sorted()`를 걸고 있었다.
`S15P11A705-252`(back#146) 이후로는 **표시값(한글) 가나다순**이다. 순서는 이미 결정적이었다.
바꿔야 할 것은 결정성이 아니라 **그 기준이 아무 의미도 없다**는 점이다 — 「가족과」가 「활기찬」보다
앞에 올 이유가 없고, 표시 라벨을 한 글자 고치면 카드에 뜨는 Keyword 구성이 바뀐다.

## 실측 — 무엇이 갈리고 무엇이 안 갈리나

시연 DB(Collection 16건 / Context 42건 / `context_keyword` 83행, PUBLIC·활성 Preset 25개)에서
`FeedKeywordRepository.COLLECTION_KEYWORDS_SQL`과 같은 집계를 돌렸다. 아래 표는 Collection을
익명 인덱스로 바꿔 적은 것이며, 측정값·순위·건수·구조 외에는 담지 않는다.

```text
Collection 당 PUBLIC Keyword 수   최소 2 · 중앙값 4 · 최대 8
Context 당 Keyword 수             0:3건  1:10건  2:16건  3:11건  4:2건   (평균 1.98)
```

| Keyword 수 | Collection 수 | 비고 |
|---|---|---|
| 5개 이상 | 6 (38%) | **4개로 자르는 일이 실제로 일어나는 구간** |
| 정확히 4개 | 6 (38%) | 자르지 않고 그대로 나간다 |
| 4개 미만 | 4 (25%) | 부족 경로. 예외가 아니라 정상 경로다 |

**빈도가 갈리지 않는다.**

```text
모든 Keyword의 빈도가 1인 Collection      10/16 (63%)
자를 필요가 있는 6건 중 빈도가 전부 1인 것   4건
```

Collection이 Record 1~5건 규모이고 Context 하나가 Keyword를 평균 2개 받으므로, 같은 Keyword가
두 번 이상 겹칠 일 자체가 드물다. **자를 필요가 있는 6건 중 4건에서는 빈도로 한 개도 고르지 못한다.**
빈도를 유일한 기준으로 두면 그 4건은 사실상 무작위 절단이 된다.

**축(category)은 갈린다.** 프리셋 27개는 네 축으로 설계돼 있다.

| category | 뜻 | PUBLIC·활성 |
|---|---|---|
| `COMPANION` | 누구와 | 5 |
| `ACTIVITY` | 무엇을 | 8 |
| `ATMOSPHERE` | 어떤 분위기 | 7 |
| `SITUATION` | 어떤 상황 | 5 |

Collection이 실제로 담은 축 수는 1~4로 흩어진다(4축 5건 · 3축 5건 · 2축 5건 · 1축 1건).

## 선택지

| 안 | 장점 | 단점 |
|---|---|---|
| (a) 표시값 가나다순 유지 + 앞 4개 | 코드 변경이 가장 작다 | 「상위」의 근거가 없다. 라벨을 고치면 카드 구성이 바뀐다 |
| (b) 빈도 내림차순 + 앞 4개 | Collection 내재 신호를 쓴다 | **자를 필요가 있는 6건 중 4건에서 아무것도 못 가른다** |
| (c) `confidence` 내림차순 | 이미 저장돼 있는 값이다 | 변별력이 없다(아래 기각 근거) |
| (d) 추천 점수(`keywordAffinity`) 재사용 | 정렬 기준이 하나로 통일된다 | **보는 사람마다 카드가 달라진다**(아래 기각 근거) |
| **(e) 축 라운드로빈 + 빈도 + preset id** | 네 축을 한 번씩 채워 카드가 한 문장으로 읽힌다. 빈도가 갈리는 곳에서는 빈도가 이긴다 | 정렬 키가 셋으로 늘고, 축 분산을 위해 더 높은 빈도를 뒤로 미루는 경우가 생긴다 |

## 결정 — (e)

Feed 응답의 `keywords`는 **Collection 내재 기준**으로 정렬해 **최대 4개**를 싣는다.

정렬 키는 사전식으로 셋이며, 셋 다 결정적이다.

```text
1  축 내 순위 오름차순    같은 category 안에서 (빈도 DESC, preset id ASC) 로 매긴 1-based 순위
2  빈도 내림차순          Collection 안에서 그 Keyword가 붙은 Context 수
3  preset id 오름차순     UNIQUE 정수라 여기서 전순서가 완성된다
```

이 순서로 정렬한 뒤 앞에서 4개를 자른다. **선정 순서가 곧 표시 순서다** — 고른 뒤 다시 정렬하지
않는다.

### 왜 Collection 내재 기준인가 — 추천 점수와 가른다

추천 점수의 `keywordAffinity`는 **보는 사람 기준**이다(요청자 Profile과의 weighted Jaccard,
`feed-scoring.md` 3.2). 그것을 표시 정렬에 쓰면 셋이 깨진다.

- **같은 Collection이 보는 사람마다 다른 Keyword를 보여준다.** "이 책은 이런 책"이라는 설명이
  성립하지 않고, 프론트가 카드를 캐시할 수도 없다.
- **Collection 특징 Cache가 `collection_id` 하나로 잡혀 있다**(`feed-profile-cache.md`). 표시가
  보는 사람에 따라 달라지면 그 Cache를 표시에 재사용할 수 없다.
- **남의 카드에 내 취향이 비친다.** 내 Profile 상위 Keyword가 남의 카드 앞자리에 오는 것 자체가
  내 Profile의 누설 경로다. Feed는 타인 데이터 접근 경로이므로 이 방향의 누설도 막는다.

그래서 `ai#92`(피드 추천 품질)와 **정책 공간을 가른다.** 저쪽은 "무엇을 고르는가"(사람 기준 선정),
이쪽은 "무엇을 보여주는가"(Collection 기준 표시)다. 둘을 같은 값으로 묶으면 추천 튜닝이 카드 표시를
말없이 바꾼다.

### 왜 축이 1순위인가 — 그리고 4의 근거

네 축은 「누구와 · 무엇을 · 어떤 분위기 · 어떤 상황」이다. 한 칸씩 채우면 카드가 **한 문장으로
읽힌다.** 같은 축 넷은 나열이지 요약이 아니다.

**프론트가 요청한 4는 축의 수와 같다.** 4를 축에서 도출한 것이 아니라, 요청된 4에 축이라는 근거를
붙이는 것이다. 대신 연동을 명세에 적어 둔다 — **프리셋의 축이 늘거나 줄면 이 수도 함께 움직인다.**
그때 프론트 레이아웃과 함께 다시 정한다.

실측 효과: 축 라운드로빈은 16건 중 **6건에서 상위 4개의 축 커버리지를 늘리고, 한 건도 줄이지
않는다.**

```text
Keyword 8개·축 4개·빈도 전부 1인 Collection   축 2 → 4
Keyword 5~7개인 Collection 4건                축 3 → 4
Keyword 5개·축 3개인 Collection               축 2 → 3
```

### 왜 엄격한 「축당 1개」가 아니라 라운드로빈인가

4축을 다 가진 Collection은 **5/16(31%)뿐**이다. 축당 1개로 못 박으면 Keyword 4개를 가진
Collection(전부 같은 축)이 1개만 내보내게 된다 — 가진 것을 안 보여주는 셈이다. 라운드로빈은 1순위로
축을 한 바퀴 돌고 남는 칸을 2순위·3순위로 채우므로, **축이 하나뿐이어도 4칸이 찬다.**

### 왜 최종 동점 규칙이 `preset id`인가 — 표시값이 아니다

- **표시값은 언제든 바뀐다.** 라벨 한 글자를 고치면 카드의 Keyword 구성이 바뀐다.
  `S15P11A705-252`(back#146)가 같은 이유로 점수 계산의 키를 `code`로 못 박았다. 같은 이유가
  순서에도 그대로 적용된다.
- `keyword_preset.id`는 UNIQUE 불변 정수이고 축 블록(1xx `COMPANION` / 2xx `ACTIVITY` /
  3xx `ATMOSPHERE` / 4xx `SITUATION`)이 이미 들어 있어, 동점일 때 축 순서로 정렬된다.
- `code`도 불변이지만 문자열 사전순이라 축 순서를 담지 못한다.

### 기각 근거

- **(c) `confidence`** — `ai.context_keyword.confidence`는 저장돼 있으나 **변별력이 없다.**
  4개 판정 모델 실측에서 mean 0.94 / std 0.03~0.10이었고, AI 파트가 이미
  "confidence는 전 모델 변별력 낮음 → 랭킹 신호로 쓰지 않음(MVP)"으로 결론지었다
  (`ai/tools/keyword_eval/REPORT.md` 테스트 C-1·C-2). 그 판단을 뒤집을 새 근거가 없다.
- **(d) 추천 점수 재사용** — 위 "왜 Collection 내재 기준인가"에서 기각.
- **프리셋 가중치** — 프리셋에 우선순위 컬럼이 없다. 새로 만들면 27개에 사람이 순위를 매겨야 하고,
  그 순위가 어떤 Collection에나 똑같이 적용된다 — Collection이 무엇에 관한 것인지와 무관해진다.
  티켓도 "프리셋 목록·가중치를 바꾸지 않는다"로 못 박았다.
- **최신성** — `ai.context_keyword`에 시각 컬럼이 없다. Context 생성 시각으로 대신할 수 있으나,
  Collection의 성격은 "최근에 담은 것"이 아니라 "전체에서 반복되는 것"이다. 빈도가 이미 그것을 잰다.

## 감수하는 것

- **더 높은 빈도가 뒤로 밀리는 경우가 있다.** 한 축이 빈도 5·4를 가지고 다른 축이 1을 가지면 순서는
  `[5, 1, 4]`가 된다. 축 분산을 1순위로 둔 대가이며, 이것이 규칙의 의도다.
- **4개는 설정값이 아니라 상수다.** 프론트가 이 수로 레이아웃을 확정하므로 배포마다 달라지면 계약이
  아니다. `feed-scoring.md`의 튜닝값들과 다른 층에 둔다 — 그쪽은 응답 계약에 드러나지 않는 내부
  랭킹 거동이다.
- **측정 표본이 작다.** Collection 16건·Context 42건이고, 그중 실사용자 기록은 일부다. 빈도가
  갈리지 않는다는 관찰은 이 규모에서 참이며, Collection이 커지면 빈도가 갈리기 시작한다. 그때도
  규칙은 그대로 동작한다 — 빈도가 갈리면 축 1순위 안에서 빈도가 이기고, 축 2순위 진입 자체가
  줄어든다.
