## 무엇을 만들었나

`GET /v1/feed/collections` 응답의 `keywords`에 **상한 4**를 두고, 무엇을 남길지 정하는 **정렬
기준**을 세웠다. 프론트가 Feed를 책장 레이아웃으로 바꾸면서 카드에 실을 Keyword 수를 고정해야
했는데, 상한도 「상위」의 근거도 코드·명세 어디에도 없었다.

```text
FeedKeywordSelector                 정렬과 절단. 순수 자바, DB·외부 호출 없음
FeedKeywordLabel                    표시값 + preset id + category
FeedKeywordRepository               표시값 조회가 id·category까지 함께 들고 온다
FeedCollectionItemResponse          KEYWORD_LIMIT = 4 (설정값 아님)
```

## 실측 — 조사가 설계를 바꾼 지점

티켓의 전제 하나가 사실과 달랐다. **현재 순서는 `GROUP BY` 결과 순서가 아니었다.**
`FeedService.RankedFeed.keywordsOf`는 `S15P11A705-120`(back#77) 때부터 `.sorted()`를 걸고 있었고,
`S15P11A705-252` 이후로는 **표시값 가나다순**이었다. 즉 순서는 이미 결정적이었다.

그래서 문제는 결정성이 아니라 **기준에 의미가 없다**는 것으로 바뀌었다. 「가족과」가 「활기찬」보다
앞에 올 이유가 없고, 더 나쁜 것은 **표시 라벨을 한 글자 고치면 카드에 뜨는 Keyword 구성 자체가
바뀐다**는 점이었다. 이것을 실행으로 확인한 것이 RED의 가장 무거운 신호였다.

```text
display_name 을 「가장앞…」 → 「힣가장뒤…」 로 바꾼 뒤

  기대   [힣가장뒤…, 나중…, 다음…]
  실제   [나중…, 다음…, 힣가장뒤…]      세 자리가 모두 이동
```

시연 DB(Collection 16 / Context 42 / `context_keyword` 83행 / PUBLIC·활성 Preset 25)에서
`COLLECTION_KEYWORDS_SQL`과 같은 집계를 돌렸다. 아래는 측정값·건수·비율만 담은 것이다.

```text
Collection 당 PUBLIC Keyword    최소 2 · 중앙값 4 · 최대 8
Context 당 Keyword              0:3  1:10  2:16  3:11  4:2      (평균 1.98)

5개 이상 → 자르는 일이 실제로 일어난다     6/16 (38%)
정확히 4개                                 6/16 (38%)
4개 미만 → 부족 경로                       4/16 (25%)

모든 Keyword의 빈도가 1인 Collection       10/16 (63%)
자를 필요가 있는 6건 중 4위·5위 동점        6/6  (100%)
```

**마지막 줄이 이 작업의 성격을 정했다.** Collection이 Record 1~5건 규모이고 Context 하나가
Keyword를 평균 2개 받으므로 같은 Keyword가 겹칠 일 자체가 드물다. 그래서 **자를 필요가 있는
Collection 전부에서 4위와 5위의 빈도가 같다** — 빈도 내림차순은 잘리는 경계를 한 건도 가르지
못하고, 그 자리는 전부 동점 규칙이 정한다.

**4개 미만은 25%다.** 대부분이 4개 미만이라 자를 일이 드문 상황은 아니다 — 75%가 4개 이상이고
38%에서 실제로 자른다. 정렬의 실효는 있고, 다만 그 실효를 빈도가 갖지 못한다.

## 무엇이 우리 결정이고 무엇이 아닌가

작업 도중 중앙 조정 세션이 프론트와의 구두 합의(2026-08-03)를 전달해 두 축이 닫혔다.

| 무엇 | 값 | 출처 |
|---|---|---|
| 개수 | 최대 4 | **프론트와 구두 합의 (2026-08-03)** |
| 정렬 | 빈도 내림차순 | **프론트와 구두 합의 (2026-08-03)** |
| **동점 규칙** | 축 내 순위 → `preset.id` | **이 작업의 결정** |

**개수 4를 데이터로 역산하지 않는다.** 4는 카드 레이아웃이 정한 값이고 그것이 정당한 근거다.
초판에서 "4 = 프리셋의 축 수"라고 적었던 것을 걷어냈다 — 측정에서 나온 값처럼 보이면 나중에
분포가 바뀔 때마다 이 값을 재계산하려 들게 된다.

**초판은 축을 전역 1순위에 뒀고, 그것이 합의된 정렬과 어긋났다.** 빈도 5·4·1을 `[5, 1, 4]`로
뒤집었기 때문이다. 축 내 순위를 `(빈도, category)` 단위로 매기도록 고쳐, 축이 **같은 빈도
안에서만** 일하게 했다. 지금은 언제나 `[5, 4, 1]`이다.

`FeedKeywordSelectorTests.frequencyOutranksAxisSpread`가 이 회귀를 막는다. **축을 전역 1순위로
올리는 구현은 빈도가 전부 같은 데이터에서 결과가 똑같아 다른 테스트를 전부 통과한다** — 빈도가
갈리는 입력을 따로 세워야 걸린다.

## 왜 동점 규칙이 곁가지가 아닌가

경계 동점을 따로 셌고, 그 숫자가 이 작업의 성격을 정했다.

```text
자를 필요가 있는 Collection (Keyword 5개 이상)     6/16
그중 4위와 5위의 빈도가 같은 것                    6/6   (100%)
```

**전부다.** 빈도 내림차순은 상위 몇 자리를 정할 뿐이고 **잘리는 자리는 한 건도 가르지 못한다.**
그래서 동점 규칙을 `preset.id` 하나로 끝내지 않고 축을 앞에 뒀다 — 6/6에서 화면을 정하는 것이
이 규칙이기 때문이다.

`preset.id`를 고른 것은 후보 넷 중 유일하게 **불변**이기 때문이다.

| 후보 | 판정 |
|---|---|
| `preset.id` 오름차순 | **채택.** UNIQUE 불변 정수라 전순서가 보장된다 |
| `display_name` 사전순 | 기각. 표시값은 바뀐다 — RED에서 라벨 하나 고치자 세 자리가 이동했다 |
| 최근 부여순 | 기각. `ai.context_keyword`에 시각 컬럼이 없다 |
| 프리셋 정의 순서 | 채택안과 같다. `id`가 곧 정의 순서다(yaml의 1xx~4xx 블록) |

`GROUP BY` 결과 순서는 후보로 두지 않았다. DB가 보장하지 않고 실행 계획이 바뀌면 함께 바뀐다.

축을 `preset.id` 앞에 둔 것은 **같은 자리를 어떻게 채울지**의 문제다. 동점 무리 안에서 축을 한
바퀴 돌리면 카드가 「누구와 · 무엇을 · 어떤 분위기 · 어떤 상황」으로 읽힌다. `id`만 쓰면 같은 축이
앞자리를 독점할 수 있다. 실측에서 상위 4개의 축 커버리지가 **16건 중 6건에서 늘고 한 건도 줄지
않았다.** 엄격한 「축당 1개」는 쓰지 않았다 — 4축을 다 가진 Collection이 31%뿐이라 못 박으면
Keyword 4개를 가진 Collection이 1개만 나간다.

## 표시 정렬을 추천 점수와 가른다

추천 점수의 `keywordAffinity`는 **보는 사람 기준**이다(요청자 Profile과의 weighted Jaccard). 그것을
표시 정렬에 쓰지 않았다.

- 같은 Collection이 **사람마다 다른 Keyword**를 보여주면 "이 책은 이런 책"이 성립하지 않는다.
- Collection 특징 Cache는 `collection_id` 하나로 잡혀 있다. 표시가 보는 사람에 따라 달라지면 그
  Cache를 표시에 재사용할 수 없다.
- **남의 카드에 내 취향이 비친다.** 내 Profile 상위 Keyword가 남의 카드 앞자리에 오는 것 자체가
  내 Profile의 누설 경로다.

그래서 `ai#92`(피드 추천 품질)와 정책 공간을 **가른다.** 저쪽은 "무엇을 고르는가"(사람 기준 선정),
이쪽은 "무엇을 보여주는가"(Collection 기준 표시)다. 묶어 두면 추천 튜닝이 카드 표시를 말없이 바꾼다.

## 정렬 키

```text
1  빈도 DESC        Collection 안에서 그 Keyword가 붙은 Context 수   프론트 합의
2  축 내 순위 ASC    같은 빈도·같은 category 안에서 preset id 순위    우리 판단
3  preset id ASC    UNIQUE 정수라 여기서 전순서가 완성된다           우리 판단
```

`preset.id`가 UNIQUE이므로 이 비교자는 **전순서**다. 같은 입력에 언제나 같은 결과가 나오며, 입력
Map의 순회 순서가 달라져도 마찬가지다.

## 거르기를 자르기보다 먼저 둔다

표시값을 못 찾은 `code`(Preset 폐기·비공개 전환)와 표시값이 겹치는 `code`는 **자리를 비우지 않고
다음 후보가 이어받는다.** 순서를 뒤집으면 4개를 요청했는데 3개가 나가고, 증상이 Preset 폐기
시점에만 산발적으로 드러난다. `code`로 대신 채우는 폴백은 그 자체가 08 §6.1 위반이므로 실패는
"영문이 뜬다"가 아니라 "덜 뜬다"여야 한다.

## 쿼리는 늘지 않았다

표시값 조회가 이미 `ai.keyword_preset`을 한 번 읽고 있어서, `id`·`category`를 같은 SELECT에
얹었다. `findPublicDisplayNames` → `findPublicKeywordLabels`로 이름이 바뀌었을 뿐 왕복 수는
그대로다(feed-tests N8 — 요청당 1회 유지, `FeedServiceTests`가 `times(1)`로 고정).

## 남은 것

- **08 §10.1 미반영.** 개수 상한 4와 순서 결정성은 클라이언트가 보는 응답 계약이므로
  `Team-PinLog/docs` `static/08_API_명세.md` §10.1이 정본이다(05 §14.6이 외부 API 정본을 08로
  위임). `docs`는 별도 레포라 이 PR에서 편집할 수 없다. 넣을 두 줄은 P46 「명세 정본」에 있고,
  `feed-recommendation.md` 3.7.1에 갱신 필요 표시를 남겼다.
- **표본이 작다.** Collection 16건·Context 42건이다. "경계가 전부 동점"은 이 규모에서 참이며,
  Collection이 커지면 빈도가 갈리기 시작해 동점 규칙의 영향이 자연히 옅어진다. 규칙을 바꿔야 할
  방향이 아니다.
- **`ai#93` 코멘트는 병합 후.** 구두 합의는 휘발되므로 아래를 그대로 남긴다. 나중에 "왜 4인가"를
  누가 물으면 이 줄이 답이 된다.

  ```text
  빈도 내림차순 · 최대 4       프론트와 구두 합의 (2026-08-03)
  동점 시 축을 돌아가며 분산    우리가 정했다 — 시연 DB 63% 에서 빈도가 전부 1이라
                              빈도만으로는 못 가른다(실측)
  ```

  **재합의는 필요 없다.** 빈도를 1순위에 둔 것이 합의를 바꾼 것이 아니라 채운 것이기 때문이다.
