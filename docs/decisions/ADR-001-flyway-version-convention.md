# ADR-001: Flyway 마이그레이션 파트별 번호 구간

- **상태**: 채택
- **날짜**: 2026-07-23
- **관련 PR/커밋**: [back#3](https://github.com/Team-PinLog/back/pull/3) (`946df11`, merge `23f1933`)
- **소유 파트**: AI 파트(컨벤션 제정) / 백엔드 전 파트(준수)

## 맥락

PinLog는 `core`(백엔드 도메인)와 `ai`(임베딩·키워드) 두 스키마를 한 PostgreSQL에 둔다. Flyway를 도입하는 시점에 마이그레이션 작성 주체가 최소 둘(백엔드 도메인, AI 파트)이고, 각자 독립 브랜치에서 마이그레이션을 추가한다. 버전 번호는 전역 단조 증가여야 하는데, 두 파트가 아무 조율 없이 다음 번호를 집으면 **같은 `V2`를 동시에 만들어 병합 시 충돌**하거나, 한쪽이 이미 배포된 번호를 재사용해 체크섬이 깨진다.

## 결정

버전 번호를 **파트별 구간으로 예약**한다.

| 구간 | 소유 | 내용 |
|---|---|---|
| `V1` | AI 파트 | 공통 기반 — `core`·`ai` 스키마 생성, `CREATE EXTENSION vector` |
| `V2`~`V99` | 백엔드 | `core` 도메인 테이블·제약 |
| `V100`~`V199` | AI 파트 | `ai` 스키마 테이블·인덱스, `core.feed_event` |
| `V200`~ | 공통 | 이후 추가분 — 작성 전 슬랙에서 번호 선점 |

규칙: 자기 구간 밖 번호를 쓰지 않는다. 구간 소진·공통 변경은 슬랙에서 선점 후 작성한다. 이미 배포된 마이그레이션은 수정하지 않고 새 버전을 추가한다. 이번 D 트랙 산출물은 `V1` + `V100`~`V102`.

## 근거

- **경계가 파일 소유와 일치한다.** "남의 파일을 수정하지 않는다"는 협업 원칙을 버전 번호에도 그대로 적용해, 리뷰 시 소유 파트가 번호만으로 드러난다.
- **실행 순서가 예측 가능하다.** 정수 순차라 `V1 → V2 → … → V100`의 적용 순서와 의존(스키마 먼저, 테이블 나중)이 리뷰에서 눈으로 보인다.
- **구간이 넉넉하다.** 백엔드 98개, AI 100개는 MVP 범위를 크게 초과하므로 조기 소진 걱정이 없다.

## 버린 대안

- **타임스탬프 버전 (`V20260723090000`)**: 동시 작성 충돌은 거의 사라지지만, 적용 순서가 시계에 의존해 리뷰에서 의존 관계가 안 보이고, 파트 소유 경계가 번호에 드러나지 않는다. 협업 규모(소수 인원, 명확한 파트)에 과하다.
- **단일 순차 + 슬랙 선점만**: 구간 없이 매번 슬랙에서 다음 번호를 잡는 방식. 마이그레이션 하나 추가할 때마다 조율 비용이 들고, 파트별 병렬 작업이 매번 직렬화된다.

## 영향

- 백엔드 도메인 마이그레이션은 `V2`부터 시작한다. `V1`은 이미 AI 파트가 스키마·extension을 만들었으므로, 백엔드는 **기존 스키마 위에 테이블만** 생성한다(`CREATE SCHEMA` 재선언 금지 → [ADR-003](ADR-003-flyway-schemas-unspecified.md) 참조).
- `core.feed_event`가 `V102`(AI 구간)에 있다. 백엔드가 `core` 테이블을 훑을 때 누락으로 오인해 중복 정의하면 안 된다 → [ADR-002](ADR-002-feed-event-ownership.md).

## 검증

- `pgvector/pgvector:pg16` 컨테이너에서 `V1 → V100 → V101 → V102` 순차 적용 성공.
- 구간 컨벤션은 [`db/migration/README.md`](../../src/main/resources/db/migration/README.md)에 명문화해 다음 작성자에게 전달.
